1. PHASE 6 GOAL AND DELIVERABLES
================================================================================

Phase 6 adds session-scoped conversational state:

    ingestion / question
        -> conversation turn
        -> pronoun and focus resolution
        -> question analysis / chain building
        -> reasoning
        -> answer
        -> context and session-provenance update

Phase 6 does NOT add durable provenance, disk persistence, statistical
co-reference, or WPF integration. Conversation state is owned by LRD_Core in an
in-memory conversation registry and is shared by NlpPipeline instances that
attach to the same conversation ID. It is lost when the session is explicitly
removed or the core is reinitialized.

Required new source file:

1. OPEN-LRD/NLP/ConversationContext.cs
   - Store bounded recent mentions, role-specific focus, turn counters, and
     session provenance entries for one conversation.
   - Resolve third-person personal pronouns from recent mentions.
   - Detect ambiguous or missing antecedents deterministically.
   - Provide provenance recording and lookup for answer caveats.

Required modified files:

2. OPEN-LRD/LRD_Core.cs
   - Add the in-memory conversation web: dictionaries keyed by conversation ID
     and by NlpPipeline instance ID.
   - Initialize the conversation dictionaries with the graph in InitializeCore.
   - Expose create/get/remove/clear conversation methods plus pipeline
     attachment lookup and removal.
   - Clear or detach conversation state when the core is reinitialized without
     mutating graph nodes.

3. OPEN-LRD/NLP/NlpTypes.cs
   - Add pronoun metadata, conversation mention, pronoun-resolution result,
     and session provenance entry types.
   - Extend NlpAnswer with a session-provenance flag.
   - Extend NlpResult with provenance entries produced by the current call.

4. OPEN-LRD/NLP/NlpOptions.cs
   - Add conversation, pronoun, focus, and provenance limits and feature flags.

5. OPEN-LRD/NLP/Lexicon.cs
   - Add pronoun person, number, and case metadata.
   - Distinguish resolvable third-person pronouns from first-person,
     second-person, reflexive, and indefinite pronouns.

6. OPEN-LRD/NLP/EntityResolver.cs
   - Accept an optional ConversationContext.
   - Resolve pronoun arguments through the context before falling back to the
     existing unresolved-pronoun behavior.

7. OPEN-LRD/NLP/QuestionAnalyzer.cs
   - Resolve anchor and object pronouns through the context-aware resolver.
   - Reject only pronouns that remain unresolved or ambiguous after context
     resolution.
   - Preserve existing question semantics and variant construction.

8. OPEN-LRD/NLP/AnswerGenerator.cs
   - Accept an optional ConversationContext.
   - Detect when selected evidence was provided earlier in this conversation.
   - Append a deterministic session-provenance caveat when appropriate.
   - Keep the existing temporary-evidence behavior when no session provenance

9. OPEN-LRD/NLP/NlpPipeline.cs
   - Attach to a core-owned ConversationContext by conversation ID.
   - Register the pipeline instance with LRD_Core and expose its ConversationID.

2. SCOPE BOUNDARIES AND NON-GOALS
================================================================================

In scope:

- Third-person personal pronouns in questions and ingestible statements.
- Subject, object, and qualifier pronoun arguments.
- Recent-mention and role-specific focus tracking.
- Follow-up questions that reuse recent entities through pronouns.
- Session-scoped provenance for facts ingested by any pipeline attached to the
  same conversation ID.
- Deterministic disclosure when answer evidence came from this session.
- Bounded context and provenance memory with FIFO eviction.
- A core-owned conversation registry that lets multiple NlpPipeline instances
  attach to and share one conversation.
- Isolation between different conversation IDs, even when pipelines share a
  core or graph.

Out of scope:

- First-person or second-person pronoun resolution.
- Gender inference or gender validation.
- Full discourse analysis, topic segmentation, or centering theory.
- Resolving pronouns across different conversation IDs.
- Implicit global sharing of one conversation by every NlpPipeline.
- Cross-process, cross-session, or durable provenance.
- Full ellipsis resolution such as "And Bob?" or "What about Monday?".
- Relative-clause pronoun resolution.
- Possessive phrase rewriting or full possessive NP resolution.
- Changes to Module 1 or Module 2 graph models, trust rules, or matching.
- WPF Tools integration; this remains Phase 7 work.

3. INTEGRATION CONSTRAINTS DISCOVERED IN THE CURRENT CODEBASE
================================================================================

1. The conversation boundary is a conversation ID, not an NlpPipeline instance.
   LRD_Core is a global singleton and already owns global in-memory state.
   Phase 6 extends it with a conversation registry so several pipelines can
   share one conversation when constructed with the same ID.

2. LRD_Core currently initializes only graph and chain state.
   InitializeCore must also initialize the conversation dictionaries and clear
   any sessions from a previous initialization. It must not mutate or delete
   graph nodes during this reset.

3. Pipeline instances need an explicit, stable identity for registry
   attachment. Add a pipeline ID generated at construction and map it to the
   selected conversation ID in LRD_Core.

4. Analyze is currently read-only.
   It performs normalization, tagging, parsing, NER, and relation extraction
   without mutating the graph. Phase 6 must keep Analyze free of graph and
   conversation updates so parsing remains deterministic and side-effect free.

5. Ask and Ingest already create EntityResolver instances.
   Both call sites must use the context-aware resolver. Existing direct
   EntityResolver construction in tests must keep working through an optional
   constructor parameter.

6. EntityResolver currently rejects every pronoun.
   It returns IsPronoun=true with the diagnostic:
       "Pronoun 'she' requires conversation context (Phase 6)."
   Phase 6 replaces this with context resolution when a context is available.
   Only unresolved or unsupported pronouns retain IsPronoun=true.

7. QuestionAnalyzer currently rejects raw pronoun arguments early.
   It checks anchor.IsPronoun and objectArgument.IsPronoun before the
   context-aware resolver can resolve them. Phase 6 must resolve first and
   reject only unresolved/ambiguous pronouns.

8. ChainBuilder currently abandons chains when either endpoint is a pronoun.
   If EntityResolver resolves the pronoun, IsPronoun becomes false and existing
   ChainBuilder behavior is sufficient. No ChainBuilder signature change is
   required.

9. Ingest currently performs no provenance recording.
   It builds chains, calls ReasoningEngine.Ingest, aggregates statuses, and
   returns. Phase 6 will record per-chain provenance after each result is
   available.

10. Ask currently has no answer-side context update.
    Phase 6 will record successful anchor/answer mentions after answer
    generation, without mutating the graph.

11. NlpPipeline has no conversation, context, or provenance accessors.
    Phase 6 attaches it to a core-owned conversation, exposes ConversationID,
    a read-only provenance view, and a reset method.

12. NlpAnswer has no session-provenance flag.
    Phase 6 adds a defaulted field so existing constructors and tests remain
    source-compatible.

13. NlpResult has no provenance list.
    Phase 6 adds an init property with an empty default, following the existing
    Chains and ReasoningResults pattern.

14. Current temporary-evidence caveat lives in AnswerGenerator.
    Session provenance must integrate without breaking the existing
    "(This fact is not yet verified.)" behavior.

15. Current Phase 5 pronoun test expects a Phase 6 placeholder.
    TestNlpAnswerDiagnostics asks "Where does she work?" on a fresh pipeline and
    expects Unsupported plus a diagnostic containing "Phase 6". Phase 6 must
    update this expectation to the new no-antecedent diagnostic while keeping
    the question Unsupported on a fresh session.

16. Node labels and aliases are the only stable entity metadata available.
    Phase 6 must not invent gender, animacy, or number data not present in the
    graph.

17. Session provenance cannot use wall-clock timestamps in answer text.
    Determinism tests require monotonic turn and sequence counters, not
    DateTimeOffset values in user-visible output.

18. Sharing a conversation across pipelines changes observable test behavior.
    Existing tests that create two pipelines on one core must either use
    distinct conversation IDs to preserve isolation or explicitly opt into the
    same ID to test sharing.

Lexicon mapping requirements:

- he/him/his -> third person, singular; subject/object/possessive forms.
- she/her/hers -> third person, singular; subject/object/possessive forms.
- it/its/itself -> third person, singular.
- they/them/their/theirs/themselves -> third person, plural/unknown number.
- I/me/my/mine/myself -> first person, not resolvable in Phase 6.
- you/your/yours/yourself/yourselves -> second person, not resolvable.
- we/us/our/ours/ourselves -> first person plural, not resolvable.
- someone/something/anyone/anything/everyone/everything/nobody/nothing/none ->
  indefinite, not resolvable.
- Reflexive third-person pronouns may be marked non-resolvable in Phase 6 even
  if their person/number is known.

    public static bool TryGetPronounInfo(string value, out PronounInfo info)

5.2 Conversation mention

    internal sealed record ConversationMention(
        Guid NodeID,
        string Label,
        string SurfaceText,
        NodeTypes NodeType,
        FrameRole Role,
        int TurnIndex,
        int Sequence,
        bool FromAnswer);

Rules:

- NodeID must be non-empty.
- Label comes from the graph node when available, otherwise from the chain node.
- SurfaceText preserves what the user or answer used.
- Role records the grammatical/semantic role used for pronoun preference.
- TurnIndex and Sequence provide deterministic recency ordering.
- FromAnswer distinguishes answer mentions from ordinary mention records.

5.3 Pronoun resolution result

    internal sealed record PronounResolution(
        Guid? NodeID,
        string? Label,
        NodeTypes NodeType,
        IReadOnlyList<Guid> CandidateNodeIDs,
        bool IsAmbiguous,
        bool IsSupported,
        IReadOnlyList<string> Diagnostics);

Semantics:

- IsSupported=false means the pronoun class is not handled in Phase 6.
- NodeID != null with IsAmbiguous=false means a unique antecedent was selected.
- IsAmbiguous=true means multiple antecedents were plausible; no guessing.
- Diagnostics always explain no antecedent, ambiguity, unsupported person, or
  successful resolution.

7. CONVERSATIONCONTEXT DESIGN
================================================================================

7.1 State and ownership

LRD_Core owns the conversation web:

    Dictionary<Guid, ConversationContext> conversations
    Dictionary<Guid, Guid> pipelineConversations

- conversations maps a conversation ID to its per-session state.
- pipelineConversations maps an NlpPipeline instance ID to its conversation ID.
- Both dictionaries are initialized in InitializeCore and are memory-only.
- They must never be serialized into the graph or treated as Web_Node data.

ConversationContext owns the state for exactly one conversation:

- Guid ConversationID (immutable and non-empty)
- int TurnIndex
- int Sequence
- Guid? FocusNodeID
- Guid? LastSubjectNodeID
- Guid? LastObjectNodeID
- Guid? LastQualifierNodeID
- Guid? LastAnswerNodeID
- IReadOnlyList<ConversationMention> Mentions (newest last internally)
- IReadOnlyList<SessionProvenanceEntry> Provenance

Use List<T> internally and expose read-only views. Do not expose mutable
collections. Because one ConversationContext may be attached to several
pipelines, all counters and collections are shared by those pipelines.

7.2 Turn lifecycle

Add:

    public void BeginTurn()

Behavior:

- Increment TurnIndex once per valid Ingest or Ask call.
- Reset Sequence only on context reset, not per turn.
- Invalid input must not increment TurnIndex.
- Analyze must never call BeginTurn.

Ask and Ingest call BeginTurn after the initial Analyze check confirms the input
is analyzable and before normalization/parsing proceeds.

7.3 Mention recording

Add:

    public void RecordMention(ConversationMention mention)
    public void RecordMentions(IEnumerable<ConversationMention> mentions)

Rules:

- Ignore empty NodeIDs.
- Remove any older mention with the same NodeID before adding the new one.
  This keeps one current role/recency record per node and prevents repeated
  questions from flooding the window.
- Cap the list to MaxConversationMentions using FIFO eviction.
- Increment Sequence for each accepted mention.
- Update role-specific focus fields:
    Subject -> LastSubjectNodeID
    Object -> LastObjectNodeID
    Location/Time/Qualifier -> LastQualifierNodeID
- Do not automatically change FocusNodeID in RecordMention; callers decide
  focus explicitly.

Focus update methods:

    public void SetFocus(Guid? nodeID, FrameRole role, bool fromAnswer)

Behavior:

- Set FocusNodeID to nodeID.
- Update the role-specific last-node field.
- If fromAnswer, set LastAnswerNodeID.
- Ignore Guid.Empty.

7.4 Focus tracking rules

After successful ingestion of a chain:

- Record the first chain node as a Subject mention.
- Record the last chain node with a role derived from the link classification:
    identities/actions -> Object
    spatial -> Location
    temporal -> Time
    basic/empty -> Qualifier
- Set focus to the last chain target, falling back to the subject.
- Do not update context for chains whose ReasoningStatus is RejectedByTrust,
  Ambiguous, NoMatch, or InvalidInput.

After a successful question answer:

- Answered: record the anchor mention using question.AnchorRole, record the
  answer node using a role derived from AnswerKind, and set focus to the answer
  node when present, otherwise the anchor.
- Yes/No: record the anchor mention and set focus to the anchor.
- Ambiguous/NoMatch/Unsupported/InvalidInput: do not change mentions or focus.
- Always increment the turn counter, even when the answer is not successful.

This policy prevents failed questions from polluting subsequent pronoun
resolution.

7.5 Pronoun resolution algorithm

Add:

    public PronounResolution ResolvePronoun(
        string surfaceText,
        NodeTypes expectedType,
        FrameRole role,
        LRD_Core core,
        NlpOptions options)

Algorithm:

1. Look up PronounInfo through Lexicon.TryGetPronounInfo.
2. If the value is not a pronoun or the info is missing, return
   IsSupported=false with a diagnostic.
3. If Person is First or Second, return IsSupported=false with:
       "First- and second-person pronouns are not supported in this session."
4. If IsReflexive or IsIndefinite, return IsSupported=false with an explicit
   unsupported-pronoun diagnostic.
5. Build a candidate list from recent mentions:
   - NodeID must still resolve through core.TryGetNode.
   - Turn distance must be <= PronounRecencyWindow.
   - Prefer mentions whose NodeType exactly matches expectedType.
   - If no type-compatible mention exists, retry without the type filter.
   - Limit to MaxPronounCandidates after scoring.
6. If no candidates remain, return IsSupported=true, NodeID=null,
   IsAmbiguous=false with:
       "Pronoun '<surface>' has no clear antecedent in this session."
7. Score each candidate deterministically:
   - Recency score: 0.20 * (1.0 / (1 + turnDistance))
   - Role match: +0.50 when mention.Role == role
   - Focus match: +0.20 when mention.NodeID == FocusNodeID
   - Answer match: +0.10 when mention.FromAnswer
   - Type match: +0.10 when mention.NodeType == expectedType
8. Sort by score descending, then TurnIndex descending, then Sequence
   descending, then NodeID string ordinal ascending.
9. If the top two candidates have different NodeIDs and their score difference
   is <= PronounAmbiguityMargin, return IsAmbiguous=true with all top-tied
   candidates and a diagnostic naming the ambiguity.
10. Otherwise return the top candidate with a diagnostic:
       "Pronoun '<surface>' resolved to '<label>'."

Gender policy:

- Phase 6 does not infer or verify gender.
- he/him/his and she/her/hers are treated as singular third-person pronouns.
- Recency and role selection decide the antecedent when only one plausible
  candidate exists.
- When multiple equally plausible candidates exist, return ambiguity rather
  than guessing.

Number policy:

- it/its is singular/unknown.
- they/them/their is treated as plural-or-unknown and may match any plausible
  recent entity.
- No graph-level number metadata is introduced in Phase 6.

7.6 No-antecedent and ambiguity behavior

- Unresolved pronoun in a question:
    EntityResolution.IsPronoun=true
    QuestionAnalyzer keeps the question unsupported
    NlpStatus.Unsupported
    Diagnostic explains no clear antecedent
- Ambiguous pronoun in a question:
    EntityResolution.IsAmbiguous=true
    QuestionAnalysis.AnchorIsAmbiguous=true
    NlpStatus.Ambiguous through existing AnswerGenerator anchor-ambiguity path
- Unresolved or ambiguous pronoun in a statement:
    ChainBuilder receives IsPronoun/IsAmbiguous and produces no chain
    NlpStatus.Unsupported with the resolver diagnostic
    No graph mutation
- Unsupported pronoun class:
    NlpStatus.Unsupported with an explicit Phase 6 limitation diagnostic

7.7 Session provenance storage and lookup

Add:

    public void RecordProvenance(SessionProvenanceEntry entry)
    public IReadOnlyList<SessionProvenanceEntry> FindProvenance(GraphPath? path)

Record rules:

- Ignore entries when EnableSessionProvenance=false.
- Cap the list to MaxSessionProvenanceEntries using FIFO eviction.
- Increment Sequence for each entry.
- Preserve insertion order for deterministic diagnostics and tests.

Lookup rules for answer caveats:

- Return no entries when path is null or has no links.
- Match an entry when both:
    - The path link's forward/inverse IDs equal the entry's IDs, and
    - The path endpoints equal the entry endpoints in either orientation.
- Only return entries with IsUsableForAnswer=true.
- Do not use labels alone for matching; labels are not unique.
- Return entries in sequence order.

7.8 Bounds and reset

Add:

    public void Clear()
    public void Reset()

Reset behavior:

- ConversationID remains unchanged.
- TurnIndex = 0.
- Sequence = 0.
- Focus and last-role IDs = null.
- Mentions and provenance lists cleared.

NlpPipeline exposes ResetConversation(), which calls context.Clear() and does
not mutate the graph. LRD_Core.RemoveConversation removes one whole session from
the registry, and LRD_Core.ClearConversations removes all sessions. Neither
operation touches graph nodes or links.

7.9 LRD_Core conversation registry and shared access

Add to LRD_Core.cs:

    private Dictionary<Guid, ConversationContext>? conversations;
    private Dictionary<Guid, Guid>? pipelineConversations;

    public Guid CreateConversation(NlpOptions options)
    public ConversationContext GetConversation(Guid conversationID)
    public bool TryGetConversation(Guid conversationID, out ConversationContext? context)
    public ConversationContext ResolveConversation(Guid? conversationID, NlpOptions options)
    public bool RemoveConversation(Guid conversationID)
    public IReadOnlyDictionary<Guid, ConversationContext>? GetConversations()
    public void ClearConversations()
    public bool RegisterPipelineConversation(Guid pipelineID, Guid conversationID)
    public bool TryGetPipelineConversation(Guid pipelineID, out Guid conversationID)
    public bool UnregisterPipelineConversation(Guid pipelineID)

Behavior:

- InitializeCore creates both dictionaries and clears any existing conversation
  state. It does not delete graph nodes.
- CreateConversation generates a new GUID, creates a ConversationContext with
  the supplied options, stores it, and returns the ID.
- ResolveConversation(null, options) creates a fresh conversation.
- ResolveConversation(nonNullID, options) returns the existing conversation or
  throws InvalidOperationException when the ID is unknown. This prevents a
  typo from silently starting an unintended session.
- GetConversation returns the shared context or throws when missing.
  TryGetConversation is the non-throwing variant.
- RemoveConversation removes the session and all pipeline attachments to it.
- ClearConversations removes every session and attachment without touching the
  graph. It is used by InitializeCore and by tests that need a clean registry.
- RegisterPipelineConversation requires the conversation to exist and records
  the pipeline-to-conversation mapping. Re-registering the same pipeline ID is
  idempotent and replaces the old mapping.
- UnregisterPipelineConversation removes only the pipeline mapping. It does not
  clear the shared conversation.
- GetConversations exposes a read-only view for diagnostics and tests.
- LRD_Core and ConversationContext are internal types in the same assembly, so
  LRD_Core may reference OPEN_LRD.NLP.ConversationContext without introducing a
  project or assembly cycle.

Access across pipelines:

- Two NlpPipeline instances share state only when constructed with the same
  conversation ID.
- A pipeline constructed without an ID gets a fresh conversation.
- Sharing is explicit and per-core; it is never inferred from the graph.
- LRD_Core remains the single authority for which conversations exist.

8.2 Pronoun path

Replace the unconditional pronoun rejection with:

1. If argument.IsPronoun and conversation is not null and
   options.EnableConversationContext and options.EnablePronounResolution:
   - Call conversation.ResolvePronoun(
       argument.SurfaceText,

       IsAmbiguous = false
       IsPronoun = false
       Diagnostics = resolution diagnostics
3. If resolution is ambiguous:
   - Return EntityResolution with IsAmbiguous=true, IsPronoun=false,
     CandidateNodeIDs populated, and resolution diagnostics.
4. If resolution is unsupported or has no antecedent:
   - Return EntityResolution with IsPronoun=true, ResolvedNodeID=null, and
     resolution diagnostics.
5. If context is absent or pronoun resolution is disabled:
   - Keep the existing unresolved-pronoun behavior, but update the diagnostic
     from "requires conversation context (Phase 6)" to
     "requires conversation context, but no context is available."

8.3 Non-pronoun path

No behavioral change. Existing label, alias, type, ambiguity, and node-ID
creation rules remain authoritative.

8.4 Important invariant

A resolved pronoun must return a real graph node ID. Phase 6 must never create a
new node labeled "she", "he", or "it" merely because resolution was attempted.

9. QUESTIONANALYZER INTEGRATION
================================================================================

9.1 Anchor pronouns

Current code rejects anchor.IsPronoun before variant construction. Keep this
check, but it now runs after context resolution:

- Resolved pronoun: anchor.IsPronoun=false, so normal anchor handling proceeds.
- Unresolved pronoun: anchor.IsPronoun=true, so the question remains
  unsupported with the resolver diagnostic.
- Ambiguous pronoun: anchor.IsAmbiguous=true, so the existing ambiguous-anchor
  path applies.

Update the diagnostic text added by QuestionAnalyzer so it does not duplicate
the resolver diagnostic. Only add a generic Phase 6 message when the resolver
did not already provide one.

9.2 Object pronouns in yes/no questions

Current code rejects objectArgument.IsPronoun before resolving the target.
Change to:

1. Resolve yesNoObject through the existing resolver.
2. Check target.IsPronoun for unresolved pronouns.
3. Check target.IsAmbiguous for ambiguous antecedents.
4. Proceed when target has a unique ResolvedNodeID.

This enables:
    "Alice sees Bob." -> "Does she see him?" -> Yes

9.3 Wh-object and wh-qualifier pronouns

No special change is needed beyond the resolver. Existing role recovery and
variant construction already handle resolved objects and qualifiers.

9.4 Diagnostics

Add no new QuestionType or AnswerKind values. Phase 6 is about resolving
arguments, not changing question classification.

Suggested resolved-pronoun diagnostic:
    "Pronoun 'she' resolved to 'Alice'."

Suggested no-antecedent diagnostic:
    "Pronoun 'she' has no clear antecedent in this session."

Suggested ambiguous diagnostic:
    "Pronoun 'she' matches multiple recent antecedents."

10. INGESTION AND CHAINBUILDER INTEGRATION
================================================================================

10.1 EntityResolver use

NlpPipeline.Ingest must create:

    new EntityResolver(core, conversation, options)

instead of the current one-argument resolver. ChainBuilder and
ReasoningEngine.Ingest signatures do not change.

10.2 Pronoun statements

Supported examples:

    "Alice works at Acme."
    "She works at Globex."        // she resolves to Alice
    "Alice sees Bob."
    "She sees him."               // she -> Alice, him -> Bob

Behavior:

- Resolved pronouns produce normal chains using the resolved node IDs.
- No chain node or graph node is created for the pronoun surface.
- Unresolved or ambiguous pronouns produce no chain and no graph mutation.
- The resulting diagnostics must state why the statement was not ingested.

10.3 Context and provenance update order

After results are produced for all chains:

1. Pair each built chain with its ReasoningResult by index.
2. For each pair, create and record a SessionProvenanceEntry when provenance
   is enabled.
3. For successful results only, record chain-node mentions and update focus.
4. Return NlpResult with Provenance set to the entries created by this call.

This ordering ensures answer caveats and later follow-up questions see the same
fact state that the reasoning results reported. Updates are written to the
core-owned conversation, so sibling pipelines attached to the same ID observe
them immediately.

10.4 Failed ingestion

- RejectedByTrust, Ambiguous, NoMatch, and InvalidInput results still receive
  provenance entries when provenance is enabled, with IsUsableForAnswer=false.
- They do not update conversation mentions or focus.
- They must not leave partial mention state from an unsuccessful chain.

11. NLPPIPELINE INTEGRATION
================================================================================

11.1 Constructor and fields

Add:

    private readonly Guid pipelineID;
    private readonly Guid conversationID;
    private readonly ConversationContext conversation;

Constructor parameter (added at the end to preserve existing calls):

    Guid? conversationID = null

Initialize:

    this.pipelineID = Guid.NewGuid();
    this.conversation = core.ResolveConversation(conversationID, this.options);
    this.conversationID = this.conversation.ConversationID;
    core.RegisterPipelineConversation(this.pipelineID, this.conversationID);

A null conversationID asks LRD_Core for a new session. A non-null
conversationID must already exist in the core registry; otherwise construction
throws InvalidOperationException. NlpPipeline never creates a private context
outside the core registry.

11.2 Public/internal accessors

Add:

    public Guid PipelineID => pipelineID;
    public Guid ConversationID => conversationID;
    public ConversationContext Conversation => conversation;
    public IReadOnlyList<SessionProvenanceEntry> Provenance =>
        conversation.Provenance;
    public void ResetConversation() => conversation.Clear();
    public void Dispose() => core.UnregisterPipelineConversation(pipelineID);

Implement IDisposable so the pipeline mapping can be removed without deleting
the shared conversation. If exposing ConversationContext publicly is
undesirable, make the accessors internal to match NlpPipeline visibility. Tests
in the smoke-test project can still access internal members because they
compile the NLP sources directly.

11.3 Ask integration

Order of operations:

1. Analyze the question as today.
2. If invalid, return unchanged and do not begin a turn.
3. Call conversation.BeginTurn() on the shared core-owned context.
4. Create EntityResolver(core, conversation, options).
5. Run QuestionAnalyzer.Analyze.
6. Evaluate variants exactly as today; Ask remains read-only with respect to the
   graph.
7. Generate the answer with AnswerGenerator.Generate(..., conversation).
8. On AnswerStatus.Answered, Yes, or No:
   - Record the anchor node mention when question.AnchorNodeID is not null.
   - For Answered, record the answer node mention when AnswerNodeID is not null.
   - Set focus to the answer node, otherwise the anchor.
9. On Ambiguous, NoMatch, Unsupported, or InvalidInput:
   - Do not record mentions or change focus.
10. Return NlpResult with Question, Answer, ReasoningResults, and any
    provenance entries created by this call (normally empty for Ask).

Read-only invariant:

- Ask must not add graph nodes, graph links, or query-only IDs to the core graph.
- Ask may update the core-owned conversation registry because that is session
  memory, not graph data.
- A turn begun by one pipeline is visible to every pipeline attached to the same
  conversation ID.

11.4 Ingest integration

Order of operations:

1. Analyze the statement as today.
2. If invalid, return unchanged and do not begin a turn.
3. Call conversation.BeginTurn() on the shared core-owned context.
4. Create EntityResolver(core, conversation, options).
5. Build chains and call ReasoningEngine.Ingest as today.
6. Record provenance and update mentions/focus as described in Section 10.
7. Return NlpResult with Chains, ReasoningResults, Frames, and Provenance.

Ingestion through any attached pipeline updates the same conversation, so later
pronoun questions through a sibling pipeline can use those mentions.

11.5 Analyze integration

No conversation registry calls, no turn increment, no provenance, no focus
changes. Analyze remains the stateless parser/analyzer facade.

11.6 Reset and lifecycle integration

ResetConversation clears mentions, focus, turn counters, and provenance for the
attached conversation. It does not delete graph nodes or links. Because the
conversation is shared, a reset through one pipeline affects every pipeline
attached to the same conversation ID. A subsequent pronoun question must behave
like a fresh session.

Dispose removes only the pipeline attachment. If no pipeline remains attached,
the session stays in LRD_Core until RemoveConversation or ClearConversations is
called. Core reinitialization clears all sessions.

13. DETERMINISM AND READ-ONLY GUARANTEES
================================================================================

Determinism:

- Use TurnIndex and Sequence, not wall-clock time, for recency and ordering.
- Sort mentions/provenance by explicit sequence values.
- Sort pronoun candidates with explicit tie-breakers.
- Deduplicate diagnostics exactly as NlpPipeline already does.
- Repeated Ask calls with the same shared context state must produce the same
  status, kind, short answer, answer node ID, and base text.
- Tests that need isolated determinism must use distinct conversation IDs or
  reset the registry between scenarios.

Read-only graph guarantees:

- Ask never mutates the graph.
- Provenance lookup never mutates the graph.
- Pronoun resolution reads node metadata only.
- Context updates and the core conversation dictionaries are bounded session
  memory, not graph data.
- ResetConversation, RemoveConversation, and ClearConversations never delete
  graph nodes or links.
- Ask may add or update conversation registry entries, but it must not add
  graph nodes, graph links, or query-only IDs.
- InitializeCore clears conversation dictionaries and reinitializes the graph;
  pipelines created before that reset must not be reused.

Mutation guarantees for ingestion:

- Resolved pronouns reuse existing graph nodes when available.
- Unresolved or ambiguous pronouns never create placeholder pronoun nodes.
- Statement ingestion uses the same trust, merge, and idempotence rules as
  Phase 4.

17. RISKS, DECISIONS, AND DEFERRED WORK
================================================================================

Resolved decisions for Phase 6:

- Session boundary is a conversation ID. LRD_Core remains the global graph
  owner and also owns the in-memory conversation registry.
- Conversation state is stored in two core dictionaries: conversations keyed by
  conversation ID and pipelineConversations keyed by pipeline instance ID.
- Sharing is explicit: pipelines share only when constructed with the same
  conversation ID. A default constructor creates a fresh conversation.
- Context updates happen only in Ingest and Ask, never in Analyze.
- Pronouns resolve to existing graph nodes only. No pronoun placeholder nodes
  are created.
- he/she/it/they are resolved by recency, role, focus, and type compatibility,
  not by gender or hidden metadata.
- Role-specific mention preference is stronger than general focus preference
  so subject pronouns prefer the last subject and object pronouns prefer the
  last object.
- Ambiguity is surfaced rather than guessed.
- First/second-person, reflexive, and indefinite pronouns are deferred.
- Focus updates only on successful ingestion or successful answers.
- Session provenance is per-conversation, shared by attached pipelines,
  bounded, and memory-only.
- Session provenance is recorded per chain with reasoning status and trust
  context.
- RemoveConversation and ClearConversations affect session state only; they
  never delete graph data.
- InitializeCore clears the conversation registry because old pipeline
  attachments are no longer valid after reinitialization.
- Session caveat takes precedence over the generic temporary-evidence caveat.
- No Module 1 or Module 2 model changes are required.
- No WPF changes in Phase 6.

Known limitations after Phase 6:

- No gender inference; he and she may resolve to the same candidate set.
- No number metadata beyond pronoun class.
- No full ellipsis or discourse structure.
- No cross-process or cross-core persistence.
- No automatic conversation expiry or idle cleanup; removal is explicit.
- No thread-safety guarantee for concurrent pipelines sharing one conversation.
- No provenance replay or durable audit trail.
- No resolution inside relative clauses or complex coordinated subjects.
- Session memory is bounded, so very old antecedents may be forgotten.
- Provenance matching uses link type and endpoints, not source text equality.
- If the same fact was both pre-existing and re-ingested in this session, the
  answer may use the session caveat because the session did provide it again.

Explicitly deferred to Phase 7:

- Final documentation pass and status wording.
- WPF Tools integration and any end-to-end UI workflow.
- Optional manual session inspection UI.
- Full solution-wide documentation polish.
