1. CONFIRMED DECISIONS
================================================================================

- Core and conversation data use a versioned, human-readable JSON snapshot with
  the .lrdlog extension.
- The core log contains graph data, conversation state, and runtime type
  definitions.
- Query/response chains are written to a separate companion log whose filename
  has _trans appended before the extension.
  Example: session.lrdlog -> session_trans.lrdlog
- Import supports Merge and Replace modes, selected by the user.
- Merge keeps existing data on ID conflicts, imports non-conflicting data, and
  reports skipped conflicts.
- Core logs and transient logs are imported separately.
- Pipeline attachments are never persisted.
- Link distances use normalized, positive doubles with LinkClass defaults and
  optional ForwardLinkTypes overrides.
- Import/export controls live in the existing Tools window.

================================================================================
2. CORE LOG FORMAT
================================================================================

Main file: selected-name.lrdlog

Header:
- format = open-lrd-core-log
- version = 1
- exportedAtUtc
- transientFile (optional companion filename, not an absolute path)

Type definitions:
- nodeTypes: id and name
- linkClasses: id and name
- forwardLinkTypes: id and name
- inverseLinkTypes: id and name
- relations: id, name, inverseName

Nodes:
- id
- nodeTypeId and nodeTypeName
- lifetime
- ttl
- weightUp and weightDown
- label
- aliases
- dataPointer: location, mediaType, byteLength, checksum

Links:
- sourceId and destinationId
- forwardTypeId and forwardTypeName
- inverseTypeId and inverseTypeName
- linkClassId and linkClassName

Conversations:
- id
- all NlpOptions values
- turnIndex and sequence
- focusNodeId
- lastSubjectNodeId
- lastObjectNodeId
- lastQualifierNodeId
- lastAnswerNodeId
- mentions in sequence order
- provenance in sequence order; each entry records the relation, roles, source
  and topic IDs, graph-mutation flags, and the coordination kind, coordination
  group, and negation kind used when the fact was extracted

Excluded from the main log:
- query and response chains
- pipeline IDs
- pipeline-to-conversation mappings

================================================================================
3. TRANSIENT LOG FORMAT
================================================================================

Companion file: selected-name_trans.lrdlog

Header:
- format = open-lrd-transient-log
- version = 1
- exportedAtUtc
- coreFile (optional parent core-log filename for display only)

Contents:
- type definitions, so the transient log can be imported independently
- ordered query chains
- ordered response chains

The chain lists are a snapshot of the chains currently held by LRD_Core, not a
history of every workbench operation. Empty queryChains and responseChains are
valid; an ingest-only session normally produces an empty companion log. The
current workbench Ask path records a response chain for a successful answer but
does not populate the core query chain.

Each chain contains:
- ordered chain-node records with the same metadata as graph nodes
- links between chain nodes with full type and class information

Pipeline attachments are excluded because pipeline IDs are process-local.

6. IMPORT MODES
================================================================================

Replace:
- Build replacement graph and conversation collections before applying them.
- Swap the complete state into LRD_Core only after validation succeeds.
- Clear query/response chains and pipeline attachments.
- Existing workbench sessions become stale and must be refreshed or reattached.
- Global runtime type registries cannot be unregistered; existing definitions
  remain available.

Merge:
- Preserve existing nodes, conversations, and type definitions.
- Skip identical duplicate nodes and links.
- If an imported node ID exists with different data:
  - keep the existing node
  - skip the imported node
  - skip imported links that touch the conflicting node
  - report the conflict
- Add non-conflicting nodes and links.
- Skip duplicate links and links with incompatible type definitions.
- Add conversations with new IDs.
- Keep existing conversations on ID conflict.
- Preserve existing query/response chains and pipeline mappings.

16. PLANNED TOOL: LARGE TEXT FILE IMPORT
================================================================================

Status: Implemented. The chunker, importer, Import-box controls, and thirteen

Scope: Add a text-file ingestion action to the Import box of the Tools window
       so a file larger than the per-call NLP limits can be ingested.
Constraint: Native C# and WPF with no external libraries.

16.1 CONFIRMED DECISIONS

- Chunking is paragraph-first with a sentence fallback, then a hard split for
  a single oversized sentence.
- A failing chunk does not stop the import. Processing continues and the run
  reports per-chunk outcomes. Successfully ingested knowledge remains.
- Provenance uses two optional GUID boxes (Source Node ID, Topic Node ID). When
  Source is blank, the tool creates a permanent Source node named after the
  file and points its DataPointer at the file path.
- All chunks share one NlpPipeline and one conversation, so pronoun and focus
  resolution can carry across adjacent chunks.
- The tool supports a Dry run checkbox and editable safety limits for file size
  and chunk count.

16.2 WHY CHUNKING IS REQUIRED

NlpPipeline.Ingest calls Analyze, which enforces NlpOptions per call:

  MaxCharacters     = 20,000 characters
  MaxSentences      = 50 sentences
  MaxTokens         = 2,000 tokens
  MaxChainsPerText  = 64 chains

A file of any useful size therefore has to be split into bounded Ingest calls.
Each call still completes a normal conversation turn and normal graph writes.

16.4 CHUNKING ALGORITHM

1. Read the file with StreamReader(UTF8, detectEncodingFromByteOrderMarks:
   true). Reject a file whose first 8 KB contain a NUL byte as binary.
2. Enforce the file-size limit before reading the whole body.
3. Split the raw text on blank lines into paragraphs. Do this before
   TextNormalizer.Normalize because normalization collapses blank lines.
4. Normalize each paragraph with TextNormalizer.Normalize. Skip paragraphs that
   normalize to empty.
5. Budget: MaxChunkCharacters = 15,000 by default (headroom under the 20,000
   per-call cap), MaxSentencesPerChunk = 40, MaxChunks = user value.
6. Paragraph fits: emit it as one chunk when it is within the character and
   sentence budgets.
7. Paragraph too large: obtain sentence spans and greedily pack sentences into
   chunks up to the budgets.
8. A single sentence still over budget: hard-split at the last comma, semicolon,
   or space before the limit. Never drop text.
9. Safety retry: if Ingest returns InvalidInput for sentence/token limits, split
   the chunk in half at the nearest sentence boundary and retry each half
   (maximum depth 3). Record a failure if a single sentence still cannot pass.

Sentence spans reuse the tokenizer's boundary rules. Factor
TextTokenizer.FindSentenceSpans into an internal helper (for example
TextChunker.FindSentenceSpans) so the tokenizer and the importer agree on
sentence boundaries. No behavior change to Tokenize is intended.

16.5 IMPORT RUNNER

New type: OPEN-LRD/NLP/TextFileImporter.cs

Options (TextImportOptions):
- FilePath, SourceNodeID?, TopicNodeID?
- DryRun
- MaxFileBytes (default 50 MB), MaxChunks (default 10,000)
- MaxChunkCharacters (default 15,000)
- Progress callback and CancellationToken

Result (TextImportResult):
- FilePath, ConversationID?
- TotalCharacters, ChunkCount, ProcessedChunks
- IngestedChunks, UnsupportedChunks, FailedChunks, SkippedChunks
- Truncated (chunk cap reached), Cancelled
- SourceNodeID?, Diagnostics (bounded list)

Run flow:
1. Validate inputs and GUIDs before touching the graph. An invalid Source or
   Topic GUID aborts with no graph mutation.
2. Read, validate, normalize, and chunk the file.
3. Dry run: stop here. Report characters, paragraphs, chunks, and sentence
   count. Do not create a pipeline, conversation, source node, or graph nodes.
4. Create the provenance source node when Source is blank:
   NodeTypes.Sources, NodeLifetime.Permanent, label "Source: <file name>",
   DataPointer.FromFilePath(path). Reuse an existing node with the same label
   and type instead of duplicating it.
5. Create one NlpPipeline(core, options) with a new conversation. Keep and
   report ConversationID so the user can attach to it later in the Workbench.
6. For each chunk, honoring cancellation between chunks:
   - Call Ingest(chunk.Text, sourceNodeID, topicNodeID).
   - Count the NlpStatus (Ingested, Unsupported, InvalidInput, other).
   - On InvalidInput from a limit, apply the split-and-retry rule.
   - Catch per-chunk exceptions, count them as FailedChunks, keep the message.
7. Dispose the pipeline in a finally block. The conversation stays in the core
   and is exported normally; the user may remove it in the Workbench.
8. Report a summary. Diagnostics are capped (for example 100 entries) with a
   final "additional diagnostics omitted" line.

Chunk cap behavior: stop after MaxChunks, set Truncated, and report that the
remainder of the file was not imported. Nothing is rolled back.

16.6 FAILURE AND CANCELLATION POLICY

- Partial knowledge is expected and accepted.
- Cancellation completes the current chunk, then stops. Already-ingested chunks
  remain.
- Limit failures are retried by splitting; only an unsplittable chunk is
  counted as failed.
- Unsupported text (no relation frames) is reported, not treated as an error.

16.7 THREADING

Run the import with Task.Run and marshal progress and status updates through the
dispatcher, mirroring the Module 4 GCIDE load. The core graph is not
thread-safe: the operator must not run Workbench ingestion or log import at the
same time. This is documented as a limitation rather than solved here.

16.11 KNOWN LIMITATIONS

- Not transactional: failures and cancellation leave partial knowledge.
- Very large imports create many conversation turns; mention and provenance
  caps mean early context is eventually evicted, so pronoun continuity weakens
  deep into a file.
- The graph is not thread-safe, so concurrent Workbench use during an import is
  unsupported.
- Sentence boundaries inherit the tokenizer heuristics; abbreviations can still
  split incorrectly.
- Plain text only. PDF, DOCX, HTML, and CSV are out of scope.
- Import trade-offs: Markdown headings, bullet markers, and tables are ingested
  as ordinary text and may produce no frames.
- No cross-file deduplication beyond the existing reasoning-engine behavior.

16.12 ACCEPTANCE CRITERIA

- A file larger than 20,000 characters imports without InvalidInput caused by
  the per-call limits.
- Every chunk is within the documented budgets; concatenating chunks loses no
  non-whitespace content.
- A blank Source creates one permanent Source node with a file DataPointer; a
  supplied Source/Topic GUID is validated before mutation.
- All chunks share one conversation, and the ConversationID is reported.
- Dry run mutates nothing.
- Failures are reported per chunk and do not stop later chunks; cancellation
  stops promptly after the current chunk.
- The solution builds with zero warnings and zero errors, and all existing

17. SEGMENTED CORE-LOG EXPORT AND IMPORT: OVERVIEW
================================================================================

Status: Implemented

Purpose
- Support full core and transient exports that exceed the existing single-file
  import ceiling while guaranteeing every emitted file is strictly smaller than
  500 MiB (500 * 1024 * 1024 bytes).
- Keep the existing single-file `.lrdlog` output and import behavior for logs
  that fit below the limit.
- Let the importer select one manifest and restore all numbered parts as one
  validated snapshot. Cross-part links must work without duplicating endpoint
  nodes or applying partial graph changes.

Accepted decisions
1. For a split core export, the requested `session.lrdlog` path becomes a small
   manifest. Data parts use incrementing, zero-padded indices:
   `session_0001.lrdpart`, `session_0002.lrdpart`, and so on.
2. The optional transient companion gets the same size guarantee. Its split
   manifest is `session_trans.lrdlog`, with parts named
   `session_trans_0001.lrdpart`, etc.
3. Importing a manifest automatically discovers, validates, and imports the
   complete part set. Selecting a `.lrdpart` directly is rejected with a message
   directing the user to the manifest. Legacy single-file logs remain importable.
4. Parts are held in a unique sibling generation directory; their manifest
   references relative paths. This prevents a new export from overwriting the
   parts used by the currently committed manifest.
5. The byte limit is checked against actual serialized UTF-8 bytes. Set
   `MaxPartBytes` to `500 MiB - 1`; counting characters or estimated object
   sizes is not sufficient. Cap the manifest too, and enforce a bounded part
   count (`MaxPartsPerExport = 10000`).
6. If an indivisible record cannot fit in an empty part, abort with the record
   kind and ID. Do not publish a partial manifest or write any file at/above the
   limit.

Manifest and part format
- Keep legacy `open-lrd-core-log` and `open-lrd-transient-log` documents
  unchanged.
- Add separate versioned format identifiers for core manifest, core part,
  transient manifest, and transient part documents; do not overload version 1
  legacy documents with partial arrays.
- Core manifest fields: format/version, export ID, exported timestamp,
  optional transient manifest filename, type definitions, aggregate node/link/
  conversation counts, and an ordered part list. Each part entry records its
  relative path, index, record kind, byte length, SHA-256, and item count.
- Each part is a compact JSON array. Its first record is a typed header carrying
  part format/version, export ID, index, and record kind. Remaining records are
  typed node, link, conversation, or chain-node records. A link may target a node
  in any part.
- Transient manifest stores type definitions and ordered part entries. Transient
  parts record query/response chain ID, chain position, node data, and optional
  following link so chains can be reconstructed across part boundaries.
- Type definitions live in the manifests, not duplicated in each part.

Exporter design
1. Stream the ordinary legacy document to a size-limited temporary file. If it
   completes below the cap, publish it as the existing `.lrdlog` file.
2. If the capped write reaches the limit, delete its partial temporary file and
   re-run serialization in segmented mode. This keeps the normal export path
   streaming and avoids buffering the whole log merely to estimate its size.
3. Segment only between complete records. Before writing a record, measure its
   compact JSON UTF-8 byte length with a bounded counting writer. Include the
   part header, array separator, record wrapper, and reserved closing bytes in
   the fit calculation. Also count actual bytes on the destination stream as a
   final guard.
4. Preserve deterministic order: nodes by GUID string; links by source,
   destination, forward type, inverse type, and class; conversations by ID;
   transient nodes by chain and sequence.
5. Write parts into a temporary generation directory. After all parts and
   checksums pass validation, move the directory into place, then publish the
   transient manifest (if any) and the core manifest last. Keep the previous
   generation available until its replacement manifest is committed; clean up
   unreferenced prior generation directories only after success.
6. Extend `CoreLogExportResult` with split status, manifest path, part count, and
   total bytes while retaining current path and item-count fields.

Importer design
- `CoreLogImporter` detects legacy full documents versus manifests and dispatches
  to the existing or multipart path respectively.
- Validate the manifest, export ID, consecutive unique indices, relative paths,
  checksums, file sizes, aggregate counts, and part-count limit before mutating
  the core. Reject path traversal and missing, corrupt, reordered, or
  mismatched-generation parts.
- Stream each part; do not use `File.ReadAllText` or deserialize all part files
  into a second complete document graph. Stage all nodes across the set before
  validating links so cross-part endpoints resolve.
- Preserve Merge/Replace semantics and no-partial-mutation guarantees. Apply
  links and conversations only after all referenced parts and records validate.
- For transient manifests, reconstruct each ordered query/response chain across
  its fragments and preserve link metadata/origins.
- Continue accepting existing single-file core and transient logs without
  requiring migration.

Tools and tests
- Keep the normal file picker on `.lrdlog` manifests; display split status, part
  count, total bytes, and the manifest path in export results.
- Tests cover single-file output, multi-part output, strict
  per-file byte bounds, deterministic part ordering/checksums, cross-part links,
  transient chain reconstruction, missing/corrupt parts, individual-part
  rejection, manifest path safety, and legacy import/export compatibility. The
  segmented round-trip test injects a small part limit to exercise rollover and
  verifies each emitted part's actual size. A full 500-MiB hardware stress run
  remains release-scale verification.

Acceptance criteria
- Every newly emitted `.lrdlog`/`.lrdpart` file is strictly smaller than 500 MiB.
- Small exports remain valid legacy single-file logs; split exports have a
  manifest and correctly ordered, indexed parts.
- Manifest import restores all nodes, links, conversations, runtime types, and
  transient chains with cross-part references intact.
- Invalid/missing parts leave the current core unchanged.
- A failed re-export leaves the previously committed manifest and its parts
  usable; unreferenced temporary files/directories are cleaned up.

================================================================================
17.1 IMPLEMENTATION DETAILS
================================================================================

Status: Implemented

Purpose
- Allow a complete core snapshot to be exported and imported when its JSON size
  exceeds the importer’s per-file limit.
- Guarantee every emitted data part is strictly smaller than 500 MiB, measured
  as actual UTF-8 bytes on disk, not estimated from character counts.
- Preserve the current single-file `.lrdlog` format for exports that fit below
  the limit. Split only oversized core or transient logs.
- Keep the numbered files importable as one validated snapshot so links may
  reference nodes in different parts without breaking Replace/Merge semantics.

Accepted decisions
1. The selected core path remains the entry point. For a split set it contains
   a small manifest; the importer follows that manifest to load all parts.
2. Use zero-padded incrementing names based on the requested log name, for
   example `session_0001.lrdpart`, `session_0002.lrdpart`. Keep each export
   generation in a unique sibling parts directory and store relative paths in
   the manifest. The index remains the final part of each data-part basename.
3. The optional transient companion receives the same size guarantee and uses
   `session_trans.lrdlog` as its manifest with `session_trans_0001.lrdpart`, etc.
4. Existing single-file core/transient logs remain supported unchanged. A single
   data record that cannot fit in an otherwise empty part is rejected with an
   explicit error; it is never written past the limit.
5. Part publication is generation-based. Write all part files into a temporary
   generation directory, validate their sizes/checksums, move that directory to
   its final unique name, then publish manifests atomically. Keep the old
   generation until the new core manifest is committed; remove stale generation
   directories only after successful publication.

File layout and records
- Single file (under limit): retain current `open-lrd-core-log` or
  `open-lrd-transient-log` JSON format.
- Split core set:
    `session.lrdlog`                     manifest (`open-lrd-core-log-manifest`)
    `session_parts_<exportId>/session_0001.lrdpart`
    `session_parts_<exportId>/session_0002.lrdpart` ...
- Split transient set:
    `session_trans.lrdlog`                manifest (`open-lrd-transient-manifest`)
    `session_parts_<exportId>/session_trans_0001.lrdpart` ...
- Manifest includes format/version, export ID, exported timestamp, runtime type
  definitions, aggregate node/link/conversation or chain counts, and each part’s
  relative filename, index, byte length, record counts, and SHA-256 checksum.
- Each part is a compact JSON array. Its first record is a header containing the
  part format/version, export ID, index, and record kind. Remaining records are
  typed node, link, conversation, or chain-node records. A chain-node record
  carries chain ID/index, position, node data, and following link when present.
- Store node records before links where practical, but the manifest and importer
  must not rely on a link destination being in the same part as its source.
  Import all nodes across the set before validating/committing links.
- Type definitions live once in the manifest. Parts refer to the manifest’s
  export ID and version; they do not repeat the full type registry.

Size enforcement and deterministic partitioning
- Define `MaxPartBytes = 500 * 1024 * 1024 - 1`, so `FileInfo.Length` is always
  strictly below 500 MiB.
- Enforce a bounded `MaxPartsPerExport` (10,000) so manifests
  also remain well below the same 500 MiB ceiling; fail before publication if
  either the part-count or manifest-size guard is exceeded.
- Keep the streaming writer. Before writing a complete record, determine its
  exact compact UTF-8 serialized length with a bounded counting writer. Include
  the current part length, separator, record envelope, and reserved JSON closing
  bytes in the fit check. If it does not fit, close the part and retry that
  record in a new part.
- Count bytes through the actual output stream as a final guard. If even an
  empty part plus its envelope cannot hold one record, abort export before
  publishing manifests and report the record kind/ID that exceeded the limit.
- Keep record order stable: nodes by ID, links by source/destination/type/class,
  conversations by ID, and chain nodes by chain and position. Exporting the same
  unchanged graph must produce the same record ordering and checksums.
- If the initial streaming write of a legacy-format temporary log crosses the
  hard limit, discard that temp file and restart using the segmented format.
  This keeps small-log exports backward-compatible without buffering the file.

Importer behavior
- `CoreLogImporter` first distinguishes legacy full logs from core manifests.
  Selecting a manifest imports the entire set; selecting a `.lrdpart` directly
  reports that the manifest must be selected.
- Validate manifest version, export ID, unique/consecutive part indices,
  safe relative paths (no absolute paths or `..` traversal), per-part byte
  limits, existence, SHA-256, and aggregate item limits before graph mutation.
- Stream parts rather than loading each part as a string. Build the staging node
  plan across all node records first, then process links and conversations.
  Apply Merge/Replace only after every part passes validation, preserving the
  current no-partial-mutation guarantee.
- Reject missing, duplicated, reordered, mismatched-export, or corrupted parts
  with a diagnostic naming the offending path/index. Do not silently import a
  subset of a manifest’s parts.
- Preserve existing importer limits at the set level; per-part limits do not
  reset the aggregate node/link/conversation limits.

Tools and API changes
- Export result reports whether output was split, the manifest path, part count,
  and total bytes. The Tools status displays these counts and the manifest path.
- Import continues to select the base `.lrdlog` manifest. The file picker need
  not expose part files as normal import choices.
- `CoreLogExportResult` gains part/manifest metadata without removing existing
  path/count fields. Existing callers that ignore new properties keep working.

Implementation phases
1. Define manifest/part DTOs, format identifiers, export-generation naming, and
   checksums. Keep legacy DTO formats unchanged.
2. Add a byte-counted record writer with rollover and single-record oversize
   handling; publish immutable generation directories and manifests safely.
3. Add manifest discovery and validation, then staged import across all parts
   while preserving Merge/Replace atomicity and legacy single-file import.
4. Split transient chain records as well as core graph records, preserving chain
   order and links that cross part boundaries.
5. Update Tools result reporting and documentation. Tests cover split naming,
   byte ceilings, deterministic ordering/checksums, missing/corrupt parts,
   individual-part rejection, cross-part node links, transient-chain
   reconstruction, and legacy round trips.
6. The automated rollover test injects a small part-size limit and checks every
   emitted part's actual byte size. A full 500-MiB stress run remains a
   release-scale verification for representative production hardware.

Acceptance criteria
- No emitted core, transient, manifest, or data-part file is 500 MiB or larger.
- Small exports retain the current single-file format; oversized exports produce
  a manifest plus indexed parts.
- Importing the manifest restores the same node/link/conversation counts and
  metadata as the original graph in both Merge and Replace modes.
- Cross-part links and chains reconstruct correctly.
- Missing/corrupt parts fail without modifying graph state.
- Export remains deterministic, uses bounded memory, and preserves the last
  committed export if a new segmented export fails before manifest publication.
