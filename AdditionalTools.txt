================================================================================
1. CONFIRMED DECISIONS
================================================================================

- Core and conversation data use a versioned, human-readable JSON snapshot with
  the .lrdlog extension.
- The core log contains graph data, conversation state, and runtime type
  definitions.
- Query/response chains are written to a separate companion log whose filename
  has _trans appended before the extension.
  Example: session.lrdlog -> session_trans.lrdlog
- Import supports Merge and Replace modes, selected by the user.
- Merge keeps existing data on ID conflicts, imports non-conflicting data, and
  reports skipped conflicts.
- Core logs and transient logs are imported separately.
- Pipeline attachments are never persisted.
- Link distances use normalized, positive doubles with LinkClass defaults and
  optional ForwardLinkTypes overrides.
- Import/export controls live in the existing Tools window.

================================================================================
2. CORE LOG FORMAT
================================================================================

Main file: selected-name.lrdlog

Header:
- format = open-lrd-core-log
- version = 1
- exportedAtUtc
- transientFile (optional companion filename, not an absolute path)

Type definitions:
- nodeTypes: id and name
- linkClasses: id and name
- forwardLinkTypes: id and name
- inverseLinkTypes: id and name
- relations: id, name, inverseName

Nodes:
- id
- nodeTypeId and nodeTypeName
- lifetime
- ttl
- weightUp and weightDown
- label
- aliases
- dataPointer: location, mediaType, byteLength, checksum

Links:
- sourceId and destinationId
- forwardTypeId and forwardTypeName
- inverseTypeId and inverseTypeName
- linkClassId and linkClassName

Conversations:
- id
- all NlpOptions values
- turnIndex and sequence
- focusNodeId
- lastSubjectNodeId
- lastObjectNodeId
- lastQualifierNodeId
- lastAnswerNodeId
- mentions in sequence order
- provenance in sequence order; each entry records the relation, roles, source
  and topic IDs, graph-mutation flags, and the coordination kind, coordination
  group, and negation kind used when the fact was extracted

Excluded from the main log:
- query and response chains
- pipeline IDs
- pipeline-to-conversation mappings

3. TRANSIENT LOG FORMAT
================================================================================

Companion file: selected-name_trans.lrdlog

Header:
- format = open-lrd-transient-log
- version = 1
- exportedAtUtc
- coreFile (optional parent core-log filename for display only)

Contents:
- type definitions, so the transient log can be imported independently
- ordered query chains
- ordered response chains

The chain lists are a snapshot of the chains currently held by LRD_Core, not a
history of every workbench operation. Empty queryChains and responseChains are
valid; an ingest-only session normally produces an empty companion log. The
current workbench Ask path records a response chain for a successful answer but
does not populate the core query chain.

Each chain contains:
- ordered chain-node records with the same metadata as graph nodes
- links between chain nodes with full type and class information

Pipeline attachments are excluded because pipeline IDs are process-local.

6. IMPORT MODES
================================================================================

Replace:
- Build replacement graph and conversation collections before applying them.
- Swap the complete state into LRD_Core only after validation succeeds.
- Clear query/response chains and pipeline attachments.
- Existing workbench sessions become stale and must be refreshed or reattached.
- Global runtime type registries cannot be unregistered; existing definitions
  remain available.

Merge:
- Preserve existing nodes, conversations, and type definitions.
- Skip identical duplicate nodes and links.
- If an imported node ID exists with different data:
  - keep the existing node
  - skip the imported node
  - skip imported links that touch the conflicting node
  - report the conflict
- Add non-conflicting nodes and links.
- Skip duplicate links and links with incompatible type definitions.
- Add conversations with new IDs.
- Keep existing conversations on ID conflict.
- Preserve existing query/response chains and pipeline mappings.

Constraint: Native C# and WPF with no external libraries.

16.1 CONFIRMED DECISIONS

- Chunking is paragraph-first with a sentence fallback, then a hard split for
  a single oversized sentence.
- A failing chunk does not stop the import. Processing continues and the run
  reports per-chunk outcomes. Successfully ingested knowledge remains.
- Provenance uses two optional GUID boxes (Source Node ID, Topic Node ID). When
  Source is blank, the tool creates a permanent Source node named after the
  file and points its DataPointer at the file path.
- All chunks share one NlpPipeline and one conversation, so pronoun and focus
  resolution can carry across adjacent chunks.
- The tool supports a Dry run checkbox and editable safety limits for file size
  and chunk count.

16.2 WHY CHUNKING IS REQUIRED

NlpPipeline.Ingest calls Analyze, which enforces NlpOptions per call:

  MaxCharacters     = 20,000 characters
  MaxSentences      = 50 sentences
  MaxTokens         = 2,000 tokens
  MaxChainsPerText  = 64 chains

A file of any useful size therefore has to be split into bounded Ingest calls.
Each call still completes a normal conversation turn and normal graph writes.

16.4 CHUNKING ALGORITHM

1. Read the file with StreamReader(UTF8, detectEncodingFromByteOrderMarks:
   true). Reject a file whose first 8 KB contain a NUL byte as binary.
2. Enforce the file-size limit before reading the whole body.
3. Split the raw text on blank lines into paragraphs. Do this before
   TextNormalizer.Normalize because normalization collapses blank lines.
4. Normalize each paragraph with TextNormalizer.Normalize. Skip paragraphs that
   normalize to empty.
5. Budget: MaxChunkCharacters = 15,000 by default (headroom under the 20,000
   per-call cap), MaxSentencesPerChunk = 40, MaxChunks = user value.
6. Paragraph fits: emit it as one chunk when it is within the character and
   sentence budgets.
7. Paragraph too large: obtain sentence spans and greedily pack sentences into
   chunks up to the budgets.
8. A single sentence still over budget: hard-split at the last comma, semicolon,
   or space before the limit. Never drop text.
9. Safety retry: if Ingest returns InvalidInput for sentence/token limits, split
   the chunk in half at the nearest sentence boundary and retry each half
   (maximum depth 3). Record a failure if a single sentence still cannot pass.

Sentence spans reuse the tokenizer's boundary rules. Factor
TextTokenizer.FindSentenceSpans into an internal helper (for example
TextChunker.FindSentenceSpans) so the tokenizer and the importer agree on
sentence boundaries. No behavior change to Tokenize is intended.

16.5 IMPORT RUNNER

New type: OPEN-LRD/NLP/TextFileImporter.cs

Options (TextImportOptions):
- FilePath, SourceNodeID?, TopicNodeID?
- DryRun
- MaxFileBytes (default 50 MB), MaxChunks (default 10,000)
- MaxChunkCharacters (default 15,000)
- Progress callback and CancellationToken

Result (TextImportResult):
- FilePath, ConversationID?
- TotalCharacters, ChunkCount, ProcessedChunks
- IngestedChunks, UnsupportedChunks, FailedChunks, SkippedChunks
- Truncated (chunk cap reached), Cancelled
- SourceNodeID?, Diagnostics (bounded list)

Run flow:
1. Validate inputs and GUIDs before touching the graph. An invalid Source or
   Topic GUID aborts with no graph mutation.
2. Read, validate, normalize, and chunk the file.
3. Dry run: stop here. Report characters, paragraphs, chunks, and sentence
   count. Do not create a pipeline, conversation, source node, or graph nodes.
4. Create the provenance source node when Source is blank:
   NodeTypes.Sources, NodeLifetime.Permanent, label "Source: <file name>",
   DataPointer.FromFilePath(path). Reuse an existing node with the same label
   and type instead of duplicating it.
5. Create one NlpPipeline(core, options) with a new conversation. Keep and
   report ConversationID so the user can attach to it later in the Workbench.
6. For each chunk, honoring cancellation between chunks:
   - Call Ingest(chunk.Text, sourceNodeID, topicNodeID).
   - Count the NlpStatus (Ingested, Unsupported, InvalidInput, other).
   - On InvalidInput from a limit, apply the split-and-retry rule.
   - Catch per-chunk exceptions, count them as FailedChunks, keep the message.
7. Dispose the pipeline in a finally block. The conversation stays in the core
   and is exported normally; the user may remove it in the Workbench.
8. Report a summary. Diagnostics are capped (for example 100 entries) with a
   final "additional diagnostics omitted" line.

Chunk cap behavior: stop after MaxChunks, set Truncated, and report that the
remainder of the file was not imported. Nothing is rolled back.

16.6 FAILURE AND CANCELLATION POLICY

- Partial knowledge is expected and accepted.
- Cancellation completes the current chunk, then stops. Already-ingested chunks
  remain.
- Limit failures are retried by splitting; only an unsplittable chunk is
  counted as failed.
- Unsupported text (no relation frames) is reported, not treated as an error.

16.7 THREADING

Run the import with Task.Run and marshal progress and status updates through the
dispatcher, mirroring the Module 4 GCIDE load. The core graph is not
thread-safe: the operator must not run Workbench ingestion or log import at the
same time. This is documented as a limitation rather than solved here.

16.11 KNOWN LIMITATIONS

- Not transactional: failures and cancellation leave partial knowledge.
- Very large imports create many conversation turns; mention and provenance
  caps mean early context is eventually evicted, so pronoun continuity weakens
  deep into a file.
- The graph is not thread-safe, so concurrent Workbench use during an import is
  unsupported.
- Sentence boundaries inherit the tokenizer heuristics; abbreviations can still
  split incorrectly.
- Plain text only. PDF, DOCX, HTML, and CSV are out of scope.
- Import trade-offs: Markdown headings, bullet markers, and tables are ingested
  as ordinary text and may produce no frames.
- No cross-file deduplication beyond the existing reasoning-engine behavior.

16.12 ACCEPTANCE CRITERIA

- A file larger than 20,000 characters imports without InvalidInput caused by
  the per-call limits.
- Every chunk is within the documented budgets; concatenating chunks loses no
  non-whitespace content.
- A blank Source creates one permanent Source node with a file DataPointer; a
  supplied Source/Topic GUID is validated before mutation.
- All chunks share one conversation, and the ConversationID is reported.
- Dry run mutates nothing.
- Failures are reported per chunk and do not stop later chunks; cancellation
  stops promptly after the current chunk.
- The solution builds with zero warnings and zero errors, and all existing
  tests plus TextImportTests pass.
