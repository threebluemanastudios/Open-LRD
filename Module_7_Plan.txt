OPEN-LRD
MODULE 7: EVENT REPRESENTATION AND CHRONOLOGICAL QUESTION ANSWERING
IMPLEMENTATION PLAN

Status: Complete (Phases 1-4)
Scope: Reified Event nodes, event time windows, temporal variance, automatic
  extraction during Ingest, chronological and quantity queries through Ask, and
  graph-count commands.
Implementation constraints: Native C# and WPF, no external dependencies.
  `Node.cs` and `Web_Node.cs` remain unchanged.

================================================================================
1. PURPOSE AND ACCEPTED DECISIONS
================================================================================

Module 7 adds a graph representation for events with optional start/end
DateTimeOffset values and relationships to participants, action, object, and
optional location. Events are created programmatically or automatically when
normal NLP ingestion recognizes a supported temporal marker. Ask can retrieve
the time window for an event or search for events overlapping a requested
interval.

Accepted decisions:
1. Do not add fields or methods to the base `Node` or `Web_Node` classes.
2. Encode event start/end instants in the existing Event node `Label` using a
   versioned, invariant ISO-8601 representation. Store zero or more event names
   in the existing `Aliases` collection. Event display code resolves the first
   non-empty alias instead of showing the encoded label.
3. Use DateTimeOffset for temporal instants. Variance defaults to
   DateTimeOffset.UtcNow and accepts a reference time for deterministic tests.
4. Event range searches use overlap semantics by default: an event is included
   if any part of its known interval overlaps the requested interval.
5. Preserve the ordinary binary relation facts generated by ingestion, and add
   the Event node and its role links only after the primary relation was
   successfully ingested.
6. Persist timestamps through existing Label and Aliases fields; no persistence
   DTO schema changes are required.
7. Keep Ask read-only. Time searches and event descriptions do not create or
   modify graph nodes.
8. Interpret relative temporal expressions against `NlpOptions.ReferenceTime`
   when set, otherwise use the current system time. Weeks use ISO 8601 Monday-
   through-Sunday boundaries. Only seconds, minutes, hours, days, weeks, months,
   and years are supported as relative-offset units in this phase.

================================================================================
2. EVENT DATA MODEL AND LABEL FORMAT
================================================================================

Event nodes use `NodeTypes.Events`. The existing Label field stores a tagged
window value of the form:

    OPEN-LRD:EVENT-WINDOW:v1|<start ISO-8601 or empty>|<end ISO-8601 or empty>

Examples:
- Both endpoints: `OPEN-LRD:EVENT-WINDOW:v1|2026-05-12T14:00:00.0000000+00:00|2026-05-12T15:00:00.0000000+00:00`
- Start only: `OPEN-LRD:EVENT-WINDOW:v1|2026-05-12T14:00:00.0000000+00:00|`
- End only: `OPEN-LRD:EVENT-WINDOW:v1||2026-05-12T15:00:00.0000000+00:00`

`EventNodeHelper` owns formatting, validation, parsing, display-name lookup, and
alias assignment. It rejects a start later than the end. If both endpoints are
absent, Label is null. Event names are stored as aliases, enabling the existing
`FindByLabel` API and entity resolver to locate events without changing base
node behavior.

================================================================================
3. EVENT LINKS AND PROGRAMMATIC CREATION
================================================================================

`LRD_Core.CreateEvent` accepts an optional event ID/name, start/end timestamps,
subject ID, verb/action, object ID, and location ID. It:
- Creates a permanent Event node and stores the window in Label.
- Stores the optional event name in Aliases.
- Reuses or creates a Concept node for the action verb.
- Links the Event to subject, action, object, and location using `has_subject`,
  `has_action`, `has_object`, and `has_location` relations.
- Adds participant links using `participated_in` where applicable.
- Adds a Time node and `has_time` link when at least one endpoint is present.
- Validates referenced endpoint IDs before changing the graph.

The binary subject/action/object facts created by normal ingestion remain
available to existing reasoning and Ask behavior.

================================================================================
4. TEMPORAL VARIANCE AND SEARCH
================================================================================

`EventTimeVariance` reports reference time, start/end deltas, duration, and one
of `Unknown`, `Past`, `Active`, or `Future`. Friendly text includes forms such as
"ended 2 hours ago", "ongoing (started 15 minutes ago)", and "starts 3 days from
now". `LRD_Core.CalculateEventTimeVariance` exposes the operation by event ID
or node instance.

`LRD_Core.FindEventsInWindow(start, end, includeOverlapping: true)` scans Event
nodes with decodable Label windows. Overlap mode returns events that intersect
the range. Strict mode returns only events wholly contained in it; unbounded
events are excluded from strict matching. Invalid search ranges are rejected.

================================================================================
5. TEMPORAL PARSING AND AUTOMATIC INGESTION
================================================================================

`TemporalExpressionParser` supports:
- ISO date/time forms and ISO dates.
- Natural dates such as `May 12, 2026`, `May 2026`, and `2026`.
- Clock times such as `14:00` and `2:00 PM`.
- Ranges expressed as `between X and Y` or `from X to Y`.
- Event statements with a date plus a clock range, date-only markers, or a
  time-only range (time-only values use the current local date/offset).

During `NlpPipeline.Ingest`, each distinct temporal relation frame is considered
once. If its ordinary primary relation is successfully ingested and the
sentence contains a parseable temporal window, the pipeline resolves the
subject, object, and optional location; creates/reuses an Event node; links the
action concept; and records the event name as a natural-language alias. Repeated
ingestion of the same name/window/roles reuses the existing Event node.

The primary relation ingestion remains the trust gate: Event extraction does
not run for rejected, unsupported, or failed primary facts.

================================================================================
6. CHRONOLOGICAL ASK BEHAVIOR
================================================================================

Individual event time:
- `When was [event name]?` resolves an Event node through its alias.
- The answer reports the date/time window and current relative variance, and
  seeds the Event node in `NlpAnswer.Candidates`.
- Events without a recorded window return a clear no-match answer while retaining
  the Event candidate for inspection.

Range and point searches:
- Supported forms include `What happened between [start] and [end]?`,
  `What happened from [start] to [end]?`, and `What happened on/in/at [point]?`.
- `on` dates resolve to the full calendar day; year/month expressions resolve to
  their complete calendar period; point clock times resolve on the current date.
- Matching uses overlap semantics and stable event ordering.
- Results synthesize readable descriptions from the Event name and linked
  subject/action/object/location roles, include event windows, and seed all
  matching Event nodes into the Workbench Candidates table.
- Empty ranges return a clear NoMatch response.

9. PHASE 2: CHRONOLOGICAL HARDENING
================================================================================

Phase 2 closes edge cases identified after the initial event implementation:

- Temporal range parsing is intent-gated to event occurrence questions such as
  "What happened between ...?", "What occurred on ...?", and "What events took
  place in ...?". Ordinary relation questions containing a date/location
  preposition remain in the normal QuestionAnalyzer/reasoning path.
- Event extraction supports intransitive and location-targeted frames. A
  location or temporal RawData complement is not incorrectly stored as the
  Event's object; the object remains optional.
- "When did [subject] [verb] [object]?" correlates the parsed subject/action,
  object, and optional location against reified Event links. Event-name and
  participant/action questions both return the Event time window.
- Individual event-time answers choose future, active, or past copula phrasing
  from EventTimeVariance.Status.
- Relative time formatting uses singular/plural units correctly ("1 hour",
  "2 hours"). Manually labeled Event nodes without a window-encoding prefix keep
  their label as the display name when they have no aliases.

Phase 2 acceptance/verification at the time of delivery:
- Tests cover temporal-query intent gating, subject/action/object correlation,
  intransitive location events, future/active/past wording, singular time units,
  and manual-label fallback.
- Verification at the Phase 2 milestone was 167 smoke tests and 287 Manual UI
  checks; app and Manual UI builds had zero warnings and zero errors.

10. PHASE 3: RELATIVE AND DEICTIC TEMPORAL EXPRESSIONS
================================================================================

Phase 3 extends temporal interpretation in both ingestion and Ask:
- Resolve yesterday/today/tomorrow; last/this/next ISO week, calendar month,
  and calendar year.
- Resolve named weekdays and month names, including optional last/this/next
  modifiers and explicit years.
- Resolve amount expressions with digits or supported number words for seconds,
  minutes, hours, days, weeks, months, and years, using `ago`, `in the past`,
  `from now`, or `from today`.
- Accept common abbreviated weekday and month names, and interpret an unmodified
  weekday/month according to whether the temporal question is future-tense.
- Use `ReferenceTime` for deterministic tests and application-level control;
  absent a value, use local system time for interpreting calendar references.
- Store resulting absolute DateTimeOffset windows in the existing Event Label
  encoding so later Ask searches and variance calculations do not depend on the
  machine clock at read time.

Phase 3 acceptance:
- Relative expressions are recognized as temporal mentions and successfully
  produce the intended Event windows during normal Ingest.
- Ask point/range searches resolve relative expressions against the same
  configured ReferenceTime and return the corresponding Events.
- ISO week boundaries are Monday through Sunday; offset units remain limited to
  the seven core units listed above.
- Existing date/time parsing, event persistence, and ordinary non-event
  questions continue to pass.

Phase 3 verification at the time of delivery: 168 smoke tests and 287 Manual UI
checks passed; application and Manual UI builds completed with zero warnings and
zero errors.

================================================================================
11. PHASE 4: QUANTITY QUESTIONS AND COUNT COMMANDS
================================================================================

Phase 4 extends Ask with relational and event quantity answers:
- Parse "How many [type] [relation] ...?" and "How much [type] ...?" as a
  quantity question with the quantified noun span and the proper answer role.
- Map common noun classes to Entities, Locations, Objects, Concepts, or Events
  so the query variants match the counted node types.
- Return an Answered NlpAnswer with `Kind = Quantity` and the numeric count as
  ShortAnswer, including zero-result counts. Preserve all counted candidate
  nodes, scores, and graph paths for the Workbench table.
- For event queries such as "How many events happened yesterday?", use the
  temporal window search and return all matching Event candidates, including a
  successful zero count when none match.
- Recognize fixed read-only commands: "Count nodes/graph", "Count facts",
  "Count links", "Count events", and "Count conversation/mentions".
- Recognize query-form Count commands, including "Count how many people work at
  Acme" and "Count events that happened yesterday", and route them through the
  same quantity Ask paths without mutating graph or conversation state.
- Harden chronological query forms: recognize future event questions such as
  "What will happen next Monday?", and fronted temporal ranges such as
  "Between May 12 and May 13, what happened?" Preserve the user's original date
  expression in range-answer headings.

Phase 4 acceptance:
- Subject-count and object-count questions report numeric counts and fluent text.
- Zero results produce a Quantity answer with ShortAnswer `0`, not a generic
  no-match response.
- All counted graph nodes remain available in the Evidence / Candidates table.
- Fixed Count commands return the appropriate total without changing the graph.
- Event quantity questions honor ReferenceTime and the same range-overlap rules.
- Future-tense, fronted-range, abbreviated-date, and natural range-heading
  behavior is covered alongside the existing relative-time and chronological
  regression cases.

Phase 4 verification: 169 smoke tests and 289 Manual UI checks pass; application
and Manual UI builds complete with zero warnings and zero errors.
