1. Documentation [DONE 2026-11-23]
   - OPEN-LRD/Foundations/GraphSynchronization.cs (thread-safety contract, Task guard,
     IsHeldByCurrentThread, and null checks are present):

GraphSynchronization.cs uses a process-wide static Monitor lock (private static readonly object _syncRoot = new object();) to serialize synchronous operations across the assembly.

Because a static global lock creates subtle hazards around reentrancy, lock-ordering deadlocks, and async code, an explicit thread-safety contract should clearly define guarantees, caller obligations, and prohibitions.

Key Risks in the Current Implementation
Reentrancy: Monitor (lock) is reentrant on the same thread. Nested calls to Execute on the same thread will succeed silently, which can violate invariant assumptions if an outer call expects exclusive, un-interleaved mutation state.

Deadlock via Lock Inversion: Because _syncRoot is static and global, any delegate passed to Execute that acquires a secondary lock (or blocks on a Task.Result / Task.Wait()) risks a classic AB-BA deadlock if another thread acquires that secondary lock first and then enters GraphSynchronization.Execute.

Async / await Incompatibility: lock cannot span await boundaries (enforced by the C# compiler for async lambdas, though passing a Func<Task> to Execute<T> compiles and immediately releases the lock when the first incomplete Task is returned, silently breaking thread safety).

Exposed References: Returning mutable graph nodes or collections from Execute<T> leaves those references unprotected once the lock exits.

Summary of Recommended Additions
Runtime Task Guard (typeof(Task).IsAssignableFrom(typeof(T))): Prevents the single most common bug with generic Execute<T> lock wrappers, where Execute(async () => ...) silently compiles as Execute<Task> and drops the lock before the task finishes.

IsHeldByCurrentThread Helper (Monitor.IsEntered(_syncRoot)): Allows internal graph methods to assert preconditions (Debug.Assert(GraphSynchronization.IsHeldByCurrentThread)) without forcing callers to redundantly re-acquire the lock.

Explicit Null Checks: Prevents NullReferenceException inside the lock block if a null delegate is passed.

3. Compact/upgrade failure paths. [DONE 2026-11-23]
   - Compaction: "Compaction rewrites the attached store" (CoreDiskStreamingTests.cs)
     covers a round trip through OpenDiskStore, MaterializeDiskStore, an addition,
     CompactTrustedDiskStore, and reopen. It also checks that no staging or backup
     directories remain.
   - Failed rewrites: "Failed store rewrites preserve the original v3 and legacy
     stores" calls PartitionedBinaryStore.Create with a record source that fails
     mid-write. Compaction and upgrade both finish through Create, so this is the
     shared failure path. Both the v3 and the legacy directories must stay
     byte-identical, leave no sibling directories, and still open with their
     original contents (legacy still read-only).
   - Limitation: an upgrade-specific failure cannot be injected through the public
     API. Records are validated when a store attaches, and in-place corruption of an
     attached store is not seen by its open readers, so a test seam would be needed
     to fail UpgradeLegacyDiskStore itself.
   - Index and data-header corruption: "Structural index and data-header corruption
     is rejected" tampers with 11 structural fields (index magic, version, count,
     entry key, entry offset, entry length; data magic, version, partition id; record
     key and CRC). After each change the manifest hash is recomputed, so the
     structural validators or lazy record reads must reject the store. The core state
     must survive each rejection.
   - The misleading comment in CoreDiskStreamingTests.cs (MalformedFoundationPayloads)
     now describes only the duplicate-key coverage it actually tests.

4. Data Partitions. [DONE 2026-11-23]
   - Index hashing is now incremental. WritePartition streams index entries to a
     temporary body file, then writes the final index (header with the known count,
     then body) through a hashing stream. The file is no longer reopened or re-read.
     The on-disk format and manifest hash definition are unchanged. The temporary
     file is always deleted (OPEN-LRD/Persistence/PartitionedBinaryStore.cs,
     WritePartition). Tests: "Index partitions are hashed as written and reject
     tampering" (CoreDiskStreamingTests.cs). The --scale checkpoint write time is
     unchanged (~1.56s), so this is a structural change rather than a speedup.
   - Paging limit/offset is implemented for GetTrustedNodeIds/GetTrustedNodes,
     GetAllTrustedLinks, GetTrustedLinksByProvenanceTarget, FindTrustedNodes,
     GetOutgoingLinks, GetIncomingLinks, and GetTrustedNodesByTarget. Outgoing and
     incoming results are now deterministically ordered by (AssertionId, Source,
     Target). Tests: "Paged link and by-target queries return deterministic pages"
     (CoreNodeGraphTests.cs).
   - Full RebuildTrustedSkillsGraph() has been removed from the rollback path.
     Link removal now validates every link before mutating, using the new
     Graph.ContainsEdge check, so the removal loop cannot fail part-way. The
     targeted undo re-adds the removed links, and a failed restore throws instead
     of silently rebuilding. Test: "Link removal keeps the skills graph synchronized"
     (CoreNodeGraphTests.cs). The rollback branch itself is not reachable through
     the public API, so it is not directly exercised.

5. ExpressionParser. [DONE 2026-11-24]
   - AST node, depth, identifier, literal, and argument limits are enforced on
     every skill entry point that takes an Expression (Math_3, Math_4, Algebra,
     SymbolicCalculus) via ExpressionParser.ValidateExpressionLimits. The parser
     also enforces them at parse time. The earlier note that Math_3/Math_4 lack
     direct validation was out of date: they reach the check through
     SymbolicCalculus before any work.
   - Probed: a balanced 3000-leaf tree (about 6000 nodes, depth 13) is rejected at
     Math_3.Simplify, Math_3.Differentiate, Math_4.Evaluate, and Math_4.Gradient.
   - Limits are checked when an Expression enters a skill entry point, not in the
     record constructors. Constructors enforce only identifier length and argument
     count. Constructor-time checks were rejected because SymbolicCalculus builds
     intermediate trees that may legitimately exceed the node limit before
     simplifying, and a constructor check would reject them.
   - Tests: "Expression AST limits are exact at node, depth, and literal boundaries"
     (FoundationHardeningTests.cs). Node-limit exactness is bracketed at 4095 (accepted)
     and 4097 (rejected) because balanced trees cannot hit exactly 4096.

6. PartitionedBinaryStore. [DONE 2026-11-24]
   - Read policy (decision 10.16, .plans/CoreRefinement.txt) is now explicit and tested.
     The earlier wording "old-reader rejection" was inaccurate: nothing rejects
     provenance-bearing bytes for legacy readers. Legacy (v1/v2) readers do not
     interpret provenance at all. Links get synthesized legacy provenance, and
     function records get none. Unknown bytes after the last recognized field are
     ignored by v3 readers. A recognized but truncated block is rejected as
     InvalidDataException.
   - Tests: "Provenance-bearing link trailing bytes follow the v3 and legacy read
     policy" and "Provenance-bearing FunctionBox trailing bytes follow the v3 and
     legacy read policy" (CoreDiskStreamingTests.cs). The function test fails if the
     legacy guard in DeserializeFunction is removed.
   - Known edge, not changed: a function payload that ends right after its result
     (the pre-provenance layout, which current writers never emit) would read a
     nonzero unknown byte as a provenance flag. Fixing it needs framing or a format
     decision, so it is left for a decision.
