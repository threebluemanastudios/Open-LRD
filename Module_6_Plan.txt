OPEN-LRD
MODULE 6: CONVERSATIONAL ASK AND NATURAL-LANGUAGE RESPONSES
IMPLEMENTATION PLAN

Status: Complete (Phases 1-4)
Scope: More natural conversational input parsing and answer generation for Ask.
Implementation constraints: Native C# and WPF; no external dependencies. Ask
  remains read-only with respect to the knowledge graph.

================================================================================
1. PURPOSE
================================================================================

Module 6 improves the conversational experience of the existing NLP Ask path.
It recognizes common social exchanges, unwraps polite and indirect questions,
accepts ordinary questions without strict punctuation, synthesizes valid
multi-answer results, and renders graph evidence in natural English.

The implementation builds on the existing NlpPipeline, QuestionAnalyzer,
ConversationContext, AnswerGenerator, and NLP Workbench. It does not replace the
reasoning engine or change the graph's underlying facts.

================================================================================
2. ACCEPTED DESIGN DECISIONS
================================================================================

1. Ask handles social dialogue and casual pleasantries, including greetings,
   well-being questions, thanks, farewells, and basic questions about the
   assistant's identity and capabilities.
2. Conversational preamble unwrapping is enabled by default. It can be disabled
   through NlpOptions for compatibility or specialized applications.
3. Multi-answer synthesis is enabled by default for wh-questions whose distinct
   answer nodes satisfy the query. Return all answer candidates and their
   evidence paths; do not discard rows merely because the displayed answer is
   synthesized.
4. Candidate node data must continue to populate the NLP Workbench's existing
   Evidence / Candidates table. The table remains useful for synthesized
   answers, ambiguous anchors, and single-answer results.
5. Multiple distinct answer nodes with different labels are a set-valued answer
   and should normally be synthesized. Multiple graph nodes with the same label
   remain an ambiguity when the system cannot distinguish their identity.
   Ambiguous anchors remain ambiguous and retain their candidate rows.
6. Social replies and query preprocessing must not add graph facts, invoke
   ingestion, or fabricate evidence. Social exchanges must not update graph
   state. Existing conversation state is changed only according to the normal
   Ask turn/update rules for successfully answered knowledge questions.
7. Responses remain honest about missing knowledge and temporary/session
   provenance. Existing short-answer, confidence, diagnostics, and provenance
   fields continue to be populated.
8. Preserve the existing native C# architecture and current NLP/Workbench
   presentation model; no external NLP or UI packages are introduced.

4. SOCIAL DIALOGUE RECOGNITION
================================================================================

Add an intent recognizer for a bounded set of common conversational exchanges.
Recognition must be deterministic and should match normalized complete utterances
or well-defined patterns, not arbitrary substring occurrences.

Initial intent groups and representative inputs:
- Greetings: "hello", "hi", "hey", "good morning", "good afternoon",
  "good evening", "howdy".
- Well-being: "how are you?", "how are you doing?", "how's it going?".
- Thanks: "thanks", "thank you", "thanks a lot".
- Farewells: "bye", "goodbye", "see you", "farewell".
- Identity: "who are you?", "what are you?".
- Capabilities/help: "what can you do?", "help".

Behavior:
- Return a normal NlpResult containing an Answered NlpAnswer, readable Text,
  concise ShortAnswer, and confidence/diagnostics consistent with the existing
  result model.
- Do not call reasoning or ingestion for a purely social exchange.
- Do not mutate the graph, conversation mentions, provenance, turn focus, or
  answer focus for a purely social exchange.
- Keep responses brief, warm, and truthful about the graph-backed system's
  capabilities. Do not imply access to facts or tools that are not available.
- Social dialogue is enabled by default and can be disabled via NlpOptions.
- Ensure greetings embedded in an actual question do not steal the question's
  intent (for example, "Hi, where does Alice work?").

================================================================================
5. CONVERSATIONAL QUESTION PREPROCESSING
================================================================================

Add a preprocessing stage that converts common polite or indirect requests into
the direct question already supported by QuestionAnalyzer. Keep the original
user input available in the result for display and diagnostics where practical.

Initial preamble patterns:
- Polite requests: "Can/could/would you tell me ...", "Please tell me ...",
  "Tell me ...".
- Epistemic requests: "Do you know ...", "Do you happen to know ...",
  "Does anyone know ...".
- Desiderative requests: "I'd like to know ...", "I would like to know ...",
  "I want to know ...".
- Boolean embedding: "if" or "whether" introduces the proposition, such as
  "Do you know if Alice is a doctor?" Normalize this to a yes/no question.
- Wh embedding: preserve and parse the wh-clause, such as
  "Can you tell me where Alice works?".
- Entity exploration: "Tell me about Alice" and "What can you tell me about
  Alice?" become an entity exploration query over Alice's known facts rather
  than an unsupported imperative.

Punctuation and syntax tolerance:
- Recognize a leading wh-word as a question even when the final question mark
  is omitted: "Where does Alice work".
- Recognize auxiliary-inversion yes/no forms without a final question mark:
  "Is Alice a doctor", "Does Alice work at Acme".
- Continue to recognize punctuation-marked declarative-form yes/no questions,
  such as "Alice is a doctor?".
- Avoid reclassifying ordinary statements as questions solely because they
  contain a wh-word or auxiliary later in the sentence.
- Add punctuation only to the normalized query passed into question analysis;
  preserve original input separately.

Preprocessing options:
- Add EnableConversationalPreambles, default true.
- Add EnableSocialDialogue, default true.
- Add EnableMultiAnswerSynthesis, default true.
- Extend NlpOptionsLog and its ToLog/FromLog mapper. Missing fields in existing
  log files must deserialize to the new defaults.

================================================================================
6. MULTI-ANSWER SYNTHESIS AND EVIDENCE PRESERVATION
================================================================================

Extend AnswerGenerator's wh-answer path to distinguish a list of valid answers
from unresolved identity ambiguity.

Synthesis behavior:
- Collect eligible candidates from the successful query evaluations, subject to
  the existing relation, type, confidence, temporary-evidence, depth, and result
  limits.
- Deduplicate repeated paths to the same node while retaining the best candidate
  record for that node.
- For distinct answer nodes, create a natural list using comma separation and a
  final "and" (for example, "Acme and Globex" or "Alice, Bob, and Carol").
- Where a supported relation template is available, make the response a fluent
  sentence with suitable agreement (for example, "Alice and Bob work at Acme.").
  Otherwise, use the concise list as Text and ShortAnswer.
- Return AnswerStatus.Answered and an appropriate answer kind for a successful
  synthesized set.
- Preserve every included AnswerCandidate with its NodeID, label, node type,
  score, depth, relation, temporary-evidence flag, and path IDs.
- Preserve the corresponding evidence paths. Candidate and evidence data must
  remain available to the Workbench's Evidence / Candidates table and related
  evidence inspection.
- Apply MaxAnswerCandidates and existing score thresholds consistently. Do not
  synthesize candidates that were filtered out by the active query constraints.

Ambiguity behavior:
- Keep ambiguous anchor resolution as AnswerStatus.Ambiguous and show all
  available anchor candidate rows.
- If candidate nodes share a display label and no available evidence distinguishes
  their identities, return Ambiguous rather than presenting a misleading list of
  indistinguishable names.
- Keep deterministic candidate and list ordering, using score, depth, label, and
  stable node ID tie-breakers as appropriate.

================================================================================
7. NATURAL-LANGUAGE RESPONSE REALIZATION
================================================================================

Improve relation-to-English realization for answer evidence sentences without
changing stored relation names or graph links.

Initial relation mappings:
- is_a: "{subject} is a/an {category}." Choose the article based on the initial
  sound heuristic supported by the project; keep the realization deterministic.
- has_property: "{subject} is {property}." For adjective complements, omit an
  article; use a safe fallback for non-adjective property values.
- part_of: "{subject} is part of {object}.".
- has_location: "{subject} is located in {place}." Use a natural preposition
  supported by the relation's stored meaning.
- participated_in: "{subject} participated in {event}.".
- Existing identity, action, and preposition relation formatting must continue to
  work, including tense inflection where supported.

Answer text:
- Keep ShortAnswer concise and suitable for direct display (for example,
  "Acme" or "Alice and Bob").
- Prefer a fluent evidence sentence in Text when reliable evidence is available.
- Keep no-match, unsupported, and ambiguity messages distinct and informative.
- Make no-match responses query-specific where possible (for example,
  "I don't know where Alice works.") without claiming the entity is unknown when
  only the requested relation is missing.
- Preserve existing provenance semantics and recognizable caveat content unless
  a separately tested wording change is approved. Do not imply verification
  beyond the evidence metadata.
- Respect MaxAnswerTextLength and keep truncation behavior deterministic.

================================================================================
8. INTEGRATION AND SAFETY REQUIREMENTS
================================================================================

- Social dialogue recognition and preamble unwrapping run before strict question
  analysis, but after input validation and without bypassing input size limits.
- Preserve command recognition for existing commands (Output, Print, Respond,
  Reply) and ensure the new social/preprocessing recognizers do not capture them
  incorrectly.
- Ask must remain graph-read-only. Query preprocessing and social replies must
  not invoke Ingest or IngestAndAnswer.
- Preserve ambiguity candidates already exposed by QuestionAnalysis and
  AnswerGenerator.
- Preserve the original utterance, normalized text, question analysis, and
  diagnostics in NlpResult wherever possible so the Workbench remains useful for
  troubleshooting.
- Keep turns and session context deterministic. A social response or failed
  question must not alter focus or mentions; successfully answered knowledge
  queries follow existing conversation update policy.
- Avoid guessing when an indirect-question pattern is incomplete or ambiguous;
  return a friendly clarification or the existing unsupported result with a
  concise explanation.

10. IMPLEMENTATION PHASES AND ACCEPTANCE CRITERIA
================================================================================

Phase 1: Input and dialogue behavior
- Add default-on options, serialization support, social intent recognition, and
  conversational preamble normalization.
- Add punctuation-tolerant question classification with statement safeguards.
- Acceptance: social utterances receive appropriate responses; configured
  preambles and punctuation-free questions enter the existing Ask path correctly;
  graph and session read-only requirements pass.

Phase 2: Answer synthesis and realization
- Synthesize distinct valid multi-answer sets while preserving candidate and
  evidence records. Add relation-specific natural-language realization and
  query-specific no-match wording.
- Acceptance: all returned answer nodes remain inspectable in the Workbench;
  distinct answers are synthesized; indistinguishable duplicate labels and
  ambiguous anchors remain explicit ambiguities; generated language matches
  evidence and relation semantics.

Phase 3: Integration and verification
- Complete serialization compatibility, Workbench UI checks, documentation,
  deterministic behavior checks, and regression testing.
- Acceptance: the solution builds with zero warnings and zero errors; all smoke
  and manual UI checks pass; existing legacy conversation logs remain readable;
  Ask never mutates the graph.

Phase 4: Conversational hardening and edge-case coverage
- Explore both incoming and outgoing graph links and retain direction-correct
  evidence for every connected fact.
- Use verb lemmatization for multi-answer agreement rather than relying solely on
  a short list of common verbs.
- Add context-aware "What about [entity]?" / "How about [entity]?" follow-ups,
  show-me preambles, preposition-fronted wh-questions, and punctuation-separated
  greetings.
- Canonicalize embedded present and past regular-verb yes/no propositions to
  auxiliary-fronted questions.
- Expand social intent variants, including explicit bye/goodbye forms, gratitude,
  greetings, identity, and capability requests.
- Persist the last question template so contextual ellipsis remains available
  after a conversation export/import.
- Acceptance: target entities with incoming links return those facts; supported
  follow-ups reuse the preceding question's subject pattern; plural answers use
  base verb forms; all variants retain candidates/evidence and Ask remains
  read-only.

Completion summary:
- Social dialogue, default-on conversational preamble unwrapping, punctuation-
  tolerant question detection, bidirectional entity exploration, contextual
  follow-ups, multi-answer synthesis, and relation-aware evidence phrasing are
  implemented.
- Conversation option serialization preserves new settings and gives older logs
  the default-on values.
- Candidate node data and evidence paths remain available to the NLP Workbench's
  Evidence / Candidates table for synthesized and ambiguous answers.
- At Module 6 completion, 165 smoke tests and 285 automated UI checks passed.
  Current integrated verification is 171 smoke tests and 375 UI checks; the
  application build completes with zero warnings and zero errors.

================================================================================
11. OUT OF SCOPE
================================================================================

- External language models, network services, or third-party NLP packages.
- Open-ended generative claims unsupported by graph evidence.
- Statistical coreference, unrestricted paraphrase understanding, or arbitrary
  conversational memory beyond the existing ConversationContext.
- Graph mutation or ingestion from Ask responses.
- Hiding, dropping, or overwriting candidate/evidence records to make synthesized
  output appear simpler.
- Replacing the existing NLP Workbench or its Evidence / Candidates table.

================================================================================
12. IMPLEMENTED COMPONENTS
================================================================================

- `SocialDialogueRecognizer` recognizes configured social intents and returns
  friendly answers without advancing conversation state or modifying the graph.
- `ConversationalQueryPreprocessor` unwraps polite, epistemic, and desiderative
  preambles, supports about-entity exploration and contextual elliptical
  follow-ups, handles punctuation-separated greeting prefixes, and normalizes
  embedded boolean questions.
- `TextTokenizer` classifies punctuation-free wh and auxiliary-inversion
  questions while preserving declarative statement classification.
- `AnswerGenerator` synthesizes distinct answer sets, retains candidates and
  evidence paths, explores incoming and outgoing links, generates graph-backed
  entity summaries, and realizes ontology relations and plural verb agreement in
  readable English.
- `NlpPipeline.Ask` integrates these features after input validation and keeps
  the original user utterance on `NlpResult`.
- `NlpOptions` and `NlpOptionsLog` include default-on social dialogue,
  conversational preambles, and multi-answer synthesis settings.
- `ConversationContext` persists the last subject question template to support
  contextual "What about [entity]?" follow-ups across turns and log round trips.
- Smoke and UI tests cover social read-only behavior, preamble handling,
  punctuation-free questions, exploration, option serialization, and
  Evidence / Candidates table population.
