================================================================================
1. PURPOSE AND SCOPE
================================================================================

Module 8 fixes dictionary definition retrieval, improves tool discoverability,
makes selected-node information easier to access, improves Visualizer label and
orbit performance, and adds multi-format file ingestion. Work is divided into
five phases, with the GCIDE Ask fix delivered before the UI and file-ingestion work.

Implementation constraints:
- Keep graph mutations within existing graph/NLP service boundaries.
- Preserve existing import/export, ontology, maintenance, text-file import, and
  Visualizer behavior unless a phase explicitly changes its location or range.
- Retain stable control names and event contracts where practical; update UI
  automation when controls intentionally move or new tabs are added.
- Parsing and ingestion must be bounded, cancellable where applicable, and
  report partial failures rather than silently dropping records.
- Do not introduce third-party parsing/UI packages without a separate decision.

Current implementation references:
- `OPEN-LRD/Tools.xaml` and `OPEN-LRD/Tools.xaml.cs`: current vertically stacked
  export, import/text-file import, ontology, maintenance, and status controls.
- `OPEN-LRD/Visualizer/VisualizerWindow.xaml`: View sidebar, Spread and label
  controls, and selected-node HUD.
- `OPEN-LRD/Visualizer/VisualizerWindow.xaml.cs`: layout handlers, layout
  generation state, selection updates, and view-control synchronization.
- `OPEN-LRD/Visualization/VisualizerOptions.cs` and `VisualizerSettings.cs`:
  spread/label option defaults, validation, and persisted settings.
- `OPEN-LRD/Visualization/FlyCamera.cs`: camera pose, movement, framing, and orbit.
- `OPEN-LRD/NLP/TextFileImporter.cs`: existing bounded, cancellable plain-text
  file ingestion through the NLP pipeline.
- `OPEN-LRD/NLP/PosTagger.cs`, `ShallowParser.cs`, `NamedEntityRecognizer.cs`,
  `QuestionAnalyzer.cs`, and `AnswerGenerator.cs`: GCIDE definition-question
  parsing, Lexeme/Sense retrieval, and answer generation.

2. PHASE 1: GCIDE DICTIONARY QUESTION ANSWERING
================================================================================

2.1 Objective
Make GCIDE definitions answerable through Ask after the corpus is loaded. A
query such as "What is commit?" must resolve `commit` as the dictionary
headword, traverse its Lexeme-to-Sense `has_sense` relationship, and return the
Sense definition rather than searching for facts about the question word
`What`.

2.2 Analysis and implementation scope
- Correct the copula-question parse path so a lowercase dictionary headword
  following "is" is not automatically classified as an adjective merely
  because it follows an auxiliary. Preserve ordinary adjective-complement and
  existing copula behavior.
- Ensure the complement after the copula is recognized as the queried anchor
  even when the headword is also a verb in another context (for example,
  `commit`). The fix should be context-aware rather than globally reclassifying
  every dictionary headword as a noun.
- Extend dictionary-aware question resolution to include GCIDE Lexeme and Sense
  node types and the `has_sense` link. Reuse the existing graph structure:
  `Lexeme --has_sense--> Sense`, with the Sense carrying the definition label.
- With one matching Sense, write `The definition of [article] [word] is [sense].`
  to the text output box and populate ShortAnswer with the definition. Include
  `a`, `an`, or `the` before the headword only when that same article appears
  before the headword in the input question; otherwise omit it.
- With multiple matching Senses, write `Multiple definitions for [article]
  [word] were found.` and return the matching Sense nodes as a candidate list
  ordered by ascending GUID. Include an article only when the same article was
  present before the headword in the question. Preserve Lexeme/Sense evidence
  paths for the Workbench.
- Preserve normal relation questions, ordinary "What is [entity]?" queries, and
  no-match behavior when no matching Lexeme/Sense or other fact exists.

2.3 Relevant implementation and test files
- `OPEN-LRD/NLP/PosTagger.cs`: context-sensitive tagging after auxiliaries.
- `OPEN-LRD/NLP/ShallowParser.cs` and `NamedEntityRecognizer.cs`: noun-phrase
  and mention generation for lowercase headwords.
- `OPEN-LRD/NLP/QuestionAnalyzer.cs`: copula anchor, expected node types, and
  dictionary relation candidates.
- `OPEN-LRD/NLP/AnswerGenerator.cs`: natural Sense-definition answer text and
  ShortAnswer/evidence output.
- `OPEN-LRD.SmokeTests/NlpTests.cs` and `OntologyTests.cs`: Ask regressions using
  loaded Lexeme/Sense graph fixtures.

2.4 Acceptance criteria
- With GCIDE entries loaded, "What is commit?" finds the Sense definition
  "To give in trust; to put into charge or keeping; to intrust; to consign; --
  used with to, unto." and writes `The definition of commit is [sense].` to the
  text output box; no article is added because the question had none.
- The fixed phrase prefix `The definition of` remains. Any optional article
  immediately before the headword is copied only if the input question contains
  that same article; otherwise it is omitted.
- A single Sense produces the requested definition sentence, a ShortAnswer with
  the definition, and Evidence / Candidates containing the `commit` Lexeme, its
  Sense, and the `has_sense` path.
- Multiple matching Senses produce `Multiple definitions for [word] were found.`
  and a candidate list ordered by ascending GUID, with evidence paths retained;
  if the question included an article before the headword, preserve it in the
  generated statement.
- "What is dog?" and a synonym/headword query such as "What is canine?" resolve
  when their GCIDE senses are present.
- Ordinary copula questions (including existing "What is Alice?" coverage),
  adjective complements, and non-dictionary Ask behavior continue to pass.
- When no matching dictionary entry or fact exists, the system returns an
  appropriate no-match response without treating `What` as the subject anchor.

- Split a pasted multi-sentence submission into individual sentences and ingest
  them sequentially as separate sentence-sized chunks in the same new
  conversation. Preserve the original sentence order and report sentence-level

- Show a useful result for empty input, accepted input, unsupported sentences,

The affected controls are `ApplySettingsButton` and the View-tab
`ResetViewSettingsButton` (handler `ResetViewSettings_Click`). The toolbar's

captured from the actual failure; do not assume its type or cause in advance.

Required investigation and behavior:
- Reproduce the reported failure by starting a sufficiently long 3D model/layout
  generation and clicking Apply Layout and sidebar Reset View while generation
  is active.
- Capture diagnostic context for any thrown exception: initiating button,
  exception type, message, stack trace, and whether a layout was active. Surface
  a concise message in Visualizer status/warnings and append the full exception
  record to `.logs/_exceptions.log`.
- Create `.logs/` and the exception log when absent; otherwise open the existing
  log in append mode. Keep one continuous log rather than replacing it per run.
  Include a timestamp, action/button, exception details, and active-rendering
  context in each appended record.
- If writing the exception log fails, preserve the original exception context
  and report the logging failure without raising a second unhandled UI exception.
- Prevent an exception from escaping an async-void UI handler and becoming an
  unhandled dispatcher exception.
- When either action is invoked during active generation, cancel the current
  rendering immediately and queue the latest requested settings. Start the
  replacement only after at least two seconds have elapsed since the latest
  click. Coordinate cancellation so old and replacement layouts never mutate
  scene state concurrently; do not silently discard the latest request.
- Append every thrown exception, including `OperationCanceledException`, to
  `.logs/_exceptions.log`. Distinguish intentional cancellation from unexpected
  failure in the record/status, and restore button/loading state in every exit

- If the original failure cannot be reproduced in a deterministic automated

  safety/state recovery using an injectable or controllable layout task.

5. PHASE 4: VISUALIZER LABEL PERFORMANCE AND RELATIVE ORBIT
================================================================================

5.1 Objectives
- Improve flight/look responsiveness when floating labels are enabled by avoiding
  per-frame work over the full graph in the default label mode.
- Add a user-selectable label mode while keeping selected-node and hovered-node
  labels available by default.
- Lower the All Visible label cap from 1,000 to 50.
- Preserve the camera's facing relative to the selected node when orbit controls
  rotate the camera around that node; do not snap the view toward the node.

5.2 Label modes and rendering behavior
- Define `VisualizerLabelMode` in the WPF-free `OPEN-LRD/Visualization/` layer:
  - `Focused`: default mode; draw floating labels only for the selected node and
    the node currently under the cursor, for at most two labels.
  - `AllVisible`: draw visible background labels using projection, sorting,
    occlusion, and badge-decluttering, up to the configured display cap.
- Keep the existing `ShowLabels` toggle. When false, return from
  `GraphLabelOverlay.OnRender` before any projection, candidate allocation,
  sorting, occlusion, or text drawing.
- In `Focused`, directly project only the selected and hovered node centers;
  skip the full-graph scan, complete-box corner projection, candidate sorting,
  and collision/occlusion passes. If selected and hovered refer to the same node,
  draw one selected-style label.
- In `AllVisible`, do not scan every node position each frame. Build a balanced
  3D spatial BVH over layout positions after each graph layout; keep the index
  until positions change. Query it with the current view frustum, bounded by
  `MaxLabelDistance`, and traverse intersecting branches near-to-far. Use a small
  leaf capacity (initially 32 node positions) so dense graph regions can still
  be bounded by the candidate budget.
- The 250-candidate budget counts only background node candidates passed to
  projection; BVH branch/leaf visits and candidates rejected before projection do
  not consume it. Apply cheap frustum and camera-distance checks before the more
  expensive complete-box corner projection. Traverse near-to-far and process at
  most 250 background candidates per frame, then apply the 50-label draw cap and
  existing decluttering. Reuse candidate buffers to avoid per-frame allocations.
- With Show Labels enabled, selected and hovered labels are always shown in both
  modes when their centers project into the viewport. They bypass the
  250-background-candidate budget and node-type visibility filtering, but do
  consume the total draw cap in All Visible mode. Set that mode's cap range to
  2-50, default 50; both priority labels fit even at the lower bound. Focused
  mode draws up to two priority labels. If selected and hovered identify the same
  node, draw one selected-style label.
- Reuse the same spatial index for `PickNode` ray queries so mouse-hover lookup
  does not scan every graph node on each pointer move. Preserve nearest-hit and
  node-type visibility behavior.
- Respect node-type visibility for background labels in both modes; selected and
  hovered labels override that filter. The selected-node information HUD remains
  independent of floating-label visibility.
- Add a `Label Mode` selector in the View tab with the accepted option names:
  `Focused (Hover & Selection)` and `All Visible (up to cap)`.
- Disable the `Max Visible Labels` control in Focused mode. In All Visible mode,
  allow a cap from 2 through 50, defaulting to 50 with whole-number steps.
- Change `DefaultMaxLabels` and the overlay/settings defaults from 1,000 to 50.
  Clamp older persisted values above 50 to 50; normalize invalid values to the
  default. A missing or invalid `labelMode` loads as Focused.
- Persist label mode and cap through `visualizer-settings.json`; sidebar Reset
  View restores Focused mode and a cap of 50. The toolbar's separate camera Reset
  behavior remains unchanged.

5.3 Relative orbit and roll behavior
- Keep the existing Alt + WASD / Arrow orbit controls and selected-node orbit
  center.
- On entering orbit controls, preserve the current camera position and facing;
  pressing Alt alone must not reposition or re-aim the camera.
- Apply the orbit position transform around the selected node to the camera
  position offset and apply that same, un-inverted rotation to camera orientation.
  A clockwise position rotation around the node's vertical axis rotates the
  camera orientation clockwise by the same angle.
- Construct one world-space orbit rotation from the input deltas in a documented
  order (world-up yaw followed by elevation about the post-yaw orbit tangent).
  Apply that rotation to the position offset and camera orientation. Never derive
  orientation by aiming at the selected node.
- Retain the +/-85-degree orbit-elevation and camera-look pitch limits. If an
  elevation input would push camera-look pitch beyond its limit, reduce the
  effective elevation delta and apply that same effective rotation to both
  position and orientation.
- Preserve camera-to-node radial distance. Orbit entry without movement leaves
  position and orientation unchanged; orbit motion applies the same rotation to
  both, with no target-facing snap.
- Add `Alt+E` for clockwise roll and `Alt+Q` for counter-clockwise roll about the
  camera's local forward axis. Without Alt and an orbit target, E/Q retain their
  existing vertical-flight behavior. Define clockwise/counter-clockwise from the
  view looking forward into the scene.
- Represent orientation with a full 3D rotation (quaternion or equivalent
  orthonormal basis) so orbit rotations and forward-axis roll compose
  without discarding roll. Preserve existing flight/look behavior when roll is
  zero. Explicit framing actions such as Center View and Frame Selected may
  continue to aim at the selected node; this change applies to orbit navigation.

5.4 Relevant implementation and test files
- `OPEN-LRD/Visualization/VisualizerOptions.cs`: label-mode enum, default mode,
  and maximum/default label cap.
- `OPEN-LRD/Visualization/GraphSnapshot.cs` or a focused spatial-index type in
  `OPEN-LRD/Visualization/`: build/rebuild the layout-position index and expose
  frustum and ray candidate queries.
- `OPEN-LRD/Visualization/VisualizerSettings.cs`: label-mode and cap migration,
  validation, and persistence.
- `OPEN-LRD/Visualization/FlyCamera.cs`: full camera orientation, co-rotating orbit
  transform, and forward-axis roll.
- `OPEN-LRD/Visualizer/GraphLabelOverlay.cs`: focused rendering fast path,
  All Visible spatial candidate query/budget, and no-label early exit.
- `OPEN-LRD/Visualizer/VisualizerWindow.xaml` and `.xaml.cs`: label-mode control,
  cap control state, settings synchronization, reset behavior, and indexed node
  picking.
- `OPEN-LRD/Visualizer/FlyCameraController.cs`: Alt+E/Q roll mapping and retaining
  E/Q vertical flight outside orbit controls.
- `OPEN-LRD.SmokeTests/VisualizerTests.cs`: defaults, settings migration,
  focused/All Visible options, spatial-index query correctness, candidate-budget
  bounds, ray-pick parity, co-rotating orbit math, and roll direction.
- `OPEN-LRD.ManualUiTests/Program.cs`: mode selection, cap enablement, settings
  persistence/reset, per-render candidate/projection/draw counts, Alt+E/Q mapping,
  and Visualizer interaction checks.

5.5 Acceptance criteria
- Fresh settings and legacy settings without `labelMode` use Focused mode.
  Unknown enum values also safely fall back to Focused.
- Focused mode draws no more than the selected and hovered labels, skips the
  full-graph projection/decluttering pipeline, and draws one label when both
  indices identify the same node.
- Turning Show Labels off performs no label projection work.
- All Visible mode remains selectable and draws no more than 50 labels. Its cap
  control is enabled only in that mode, accepts values from 2 to 50, and defaults
  and resets to 50.
- All Visible projects no more than 250 background candidates per frame (plus
  selected/hovered priority candidates) after spatial-index filtering. The budget
  counts only candidates passed to projection, not BVH visits or early rejects.
  The selected and hovered labels are always prioritized and consume slots in
  the total All Visible draw cap; at cap 2 they take both slots.
- Focused and All Visible modes reuse a layout-built index; node-position changes
  rebuild it, while camera movement alone does not.
- Background labels respect hidden node types, while selected/hovered labels
  remain visible above that filter; Show Labels off suppresses both priority and
  background labels.
- Indexed hover/ray picking returns the same nearest visible node as a reference

6.2 Format handling
- Plain text: route through `TextFileImporter` with its existing chunking,
  provenance, dry-run, cancellation, and size-limit behavior. Plain-text files
  use NLP mode; Structured Data mode is unavailable for plain text.
- Detect format by extension, display it in the UI, and allow an explicit format
  override. A parse failure reports the selected format; never silently fall back
  to plain-text parsing.
- Structural relationship names are a fixed Phase 5 registry set with reserved,
  stable IDs. Use `has_record`, `has_table`, `has_row`, `has_cell`, `has_child`,
  `has_item`, `has_attribute`, and `has_value`; reuse existing `has_property`.
  Use `LinkClass.basic` for hierarchy/table relationships and
  `LinkClass.properties` for property/attribute/value relationships. Never
  derive relation names from user-provided headers, JSON keys, or XML tags.
- CSV: use a streaming RFC-4180-style parser supporting quoted fields, escaped
  quotes, delimiters, and line endings. One or more wholly blank records separate
  tables; each non-empty section starts with a header row. Treat all table widths
  with the same schema. A row whose cell count differs from its header is a failed
  record; report it and continue at the next recoverable row.
  - Create a `NodeTypes.Basics` Table node, Alias `Table`, Label `table_N` with a
    zero-based per-file index. Link Source -> Table with `has_table`.
  - Header row is index 0. Row-head Label and cell-count Alias use invariant
    integer strings. Header cells retain their original text and use Alias
    `HEADER`; connect them in column order with `has_cell`.
  - Data rows use invariant row-index labels and cell-count aliases. Each cell
    retains its original text as Label and corresponding header as Alias.
    Connect Source -> Table -> row heads with `has_table`/`has_row`, then chain
    each row's cells with `has_cell`; do not add Source-to-row or peer-cell links.
  - Give tables, row heads, header cells, and data cells stable file-URI fragments
    (`#table_N`, `#table_N/row_R/column_C`). This keeps identical local table names
    and repeated cell values in separate source positions distinct.
- JSON: stream one UTF-8 JSON value. A root object or scalar is one record; a root
  array has one record per item. Link Source to a synthetic root Element (Label
  `root`, Alias `JSON Element`) by `has_record`.
  - Objects use `NodeTypes.Basics` Element nodes. Properties use
    `OntologyTypes.Properties`, Label = exact key, Alias `Property`; link Element
    -> Property with `has_property`.
  - Primitive properties link Property -> Value with `has_value`. Nested objects
    link Property -> child Element with `has_child`. Arrays link Property -> an
    Item node with `has_item`; Item Alias is `array_N`. Object/array items recurse;
    scalar items link Item -> Value with `has_value`.
  - Values use `OntologyTypes.MetadataValues`. Preserve the source lexeme as
    Label and classify JSON values by token type with Alias `numberValue`,
    `booleanValue`, `stringValue`, or `nullValue`; absolute supported URIs use
    `pathValue`. Empty strings remain empty-label `stringValue` nodes; JSON null
    is Label `null`, Alias `nullValue`.
- XML: stream with `XmlReaderSettings` using `DtdProcessing.Prohibit` and
  `XmlResolver = null`. Link the document root from Source by `has_record`; each
  direct child element is a record boundary, or the root is one record if it has
  no child elements. Commit complete record subtrees as they are parsed.
  Elements use `NodeTypes.Basics`, Alias `XML Element`, and expanded-name labels
  `{namespace-uri}local-name` so prefix changes do not change identity. Child
  elements link by `has_child`. Attributes use `OntologyTypes.Properties`, Alias
  `XML Attribute`, and `has_attribute`; link them to typed Values with `has_value`.
  Preserve non-whitespace text nodes in document order, including mixed content,
  as typed Values linked by `has_value`; empty leaf elements create empty-string
  Values. Include stable element/attribute/text positions in file-URI fragments.
- Typed values: classify JSON from its native token. CSV/XML recognize booleans,
  invariant-culture numbers, and absolute supported URIs; otherwise use
  `stringValue`. Preserve original text in Value Labels. Empty CSV cells remain
  explicit empty-string Values to preserve row/cell positions.
- Extract Text for NLP mode is selected per file and uses one new `NlpPipeline`
  conversation per non-dry-run import:
  - CSV rows with normalized headers `Subject`, `Predicate`/`Relation`, and
    `Object` become `subject predicate object.` sentences. Other rows become
    ordered `header: value` text, omitting empty cells.
  - For each JSON record, if known prose keys (`text`, `content`, `body`,
    `description`, `message`, `summary`) occur, extract their string values in
    document order. Otherwise extract all string leaf values in document order.
  - XML extracts non-whitespace text nodes in document order; attributes are not
    included by default. Plain text uses the existing `TextFileImporter`.
- Reject files larger than 500 MiB before parsing or graph mutation. Use streaming
  parsers for CSV/JSON/XML, bounded to 10,000 records, 32 nested JSON/XML levels,
  1,000 CSV columns, and 15,000 characters per value. Keep at most 100 diagnostic
  messages and report when diagnostics are truncated.
- Dry run validates and summarizes without graph mutation, trust updates, Source
  node creation, or persistent conversations. Cancellation is cooperative between
  records; already committed records remain and are reported as partial import.

6.3 Graph semantics and operational guarantees
Phase 5's data contracts and graph semantics are now specified as follows:
- The fixed structural relations are registered once with stable ontology IDs:
  `has_record` 20, `has_table` 21, `has_row` 22, `has_cell` 23, `has_child` 24,
  `has_item` 25, `has_attribute` 26, and `has_value` 27. Reuse `has_property` ID 4.
  Hierarchy/table relations use `LinkClass.ontology`; property/attribute/value
  relations use `LinkClass.properties`. File values never add relation types.
- Source identity is the normalized absolute file URI in `DataPointer.Location`.
  Resolve with `Path.GetFullPath` and canonical URI escaping; compare paths
  case-insensitively on Windows. Moving/renaming a file creates a new Source.
  Content SHA-256 distinguishes revisions at the same path and is stored on the
  Source DataPointer only after a complete import.
- Skip an unchanged file only when its stored checksum matches and Source
  `TrustRating > 0.80`. Changed content at the same path is reprocessed even when
  the previous rating is higher. Partial/cancelled/truncated imports do not update
  the completed checksum or trust, so a retry cannot be skipped. A legacy Source
  without a checksum is processed once to establish the checksum. Empty files
  warn and create no Source or data nodes.
- Structural records carry stable source-specific DataPointer fragments:
  CSV table/row/column positions, JSON Pointer paths (RFC 6901), and XML expanded
  names plus sibling/text indexes. Same-source re-import upserts these positions.
  Structural cells/elements remain position-distinct; semantic entities produced
  by NLP use the duplicate policy below.
- A semantic duplicate has the same NodeType and normalized Label (trim, collapse
  internal whitespace, compare case-insensitively), unless both nodes have
  non-null, unequal DataPointers. A duplicate found from a new Source is reused,
  linked into the new structure, adds exactly one to its `weightUp`, and counts
  as a successful read. Same-source re-import never increases `weightUp`; newly
  recovered non-duplicate entities may be added.
- Count trust outcomes per record/chunk: text uses TextFileImporter chunks; CSV
  uses data rows (headers are structural metadata); JSON uses each root-array item
  or its single root value; XML uses each direct child of the document root, or
  the root itself if it has no child elements. A syntactically valid but
  unsupported NLP unit is successful. Malformed/failed records are failures;
  warnings alone are not failures.
- A complete non-dictionary import computes `Trust = 0.30 + 0.60 * S / (S + F)`.
  Thus no failures gives 90%, all failures gives 30%, and `S + F == 0` leaves the
  rating unchanged. Dictionary Source trust is 100%; manual `user` Source trust
  remains 50%. Store the complete import rating on the Source and inherited trust
  on newly created nodes. A reused semantic node keeps the greater of its current
  rating and the current Source rating.
- Update Source trust only after a complete import. On a complete same-source
  re-import, raise trust only when the new score is higher; never lower it.
- Maintenance survivor selection is trust-first: higher `TrustRating` always
  stays, even if the lower-trust node is permanent or has higher `weightUp`.
  Missing trust is 0.0. On equal trust, tie-break by permanence, higher
  `weightUp`, link count, DataPointer presence, then GUID order. Merge metadata
  preserves the maximum TrustRating and maximum `weightUp` (not their sum), plus
  aliases, maximum WeightDown, and maximum TTL.
- The 500 MiB, 10,000-record, 32-depth, 1,000-column, 15,000-character-value,
  and 100-diagnostic limits are enforced. Recoverable bad CSV rows/records are
  failed and skipped; fatal JSON/XML document syntax stops parsing. Earlier
  committed records remain and are reported. Cancellation is checked between
  records, with no rollback of already committed graph changes.
- Dry run uses the same format, schema, type, and limit validation but does not
  create graph nodes, update trust/checksum, or persist a conversation. Graph
  mutation uses the existing supported Core APIs.

8.6 Phase 4 pitch/yaw limit decision
- Phase 4 retains +/-85-degree limits for direct camera pitch and orbit elevation.
  The co-rotating orbit operation reduces its effective elevation delta if needed so
  the same applied transform still governs position and camera orientation.
- Yaw has no visual rotation limit. Quaternion storage plus the derived `atan2`
  yaw property naturally wraps equivalent angles without an ever-growing numeric
  accumulator.
- Removing yaw limits would not expand the camera's orientation range; yaw is
  already unlimited. Removing pitch/elevation limits would permit pole crossing
  and upside-down views. The quaternion camera basis remains mathematically valid,
  but the current spherical orbit calculation would need to be replaced with
  direct quaternion rotation of the position offset to avoid azimuth discontinuity
  at the poles. Movement and roll controls could also feel inverted when upside
  down. Keep the current pitch/elevation limits unless removal is separately
  confirmed, and add pole-crossing/recovery tests before changing that policy.
