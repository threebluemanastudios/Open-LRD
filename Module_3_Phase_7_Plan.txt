3. CURRENT BASELINE AND INTEGRATION CONSTRAINTS
================================================================================

Current implementation facts:

1. LRD_Core is a singleton accessed through LRD_Core.Instance.
   - InitializeCore resets the graph, query/response chains, conversations, and
     pipeline mappings.
   - Existing NlpPipeline instances must not be reused after InitializeCore.
   - CreateConversation, GetConversation, TryGetConversation,
     ResolveConversation, RemoveConversation, ClearConversations,
     RegisterPipelineConversation, TryGetPipelineConversation, and
     UnregisterPipelineConversation already exist.

2. NlpPipeline is internal, sealed, and IDisposable.
   - Constructor requires an initialized core.
   - Constructor parameters are core, optional NlpOptions, optional
     ReasoningEngine, and optional conversation ID.
   - A null conversation ID creates a fresh conversation.
   - A non-null unknown conversation ID throws InvalidOperationException.
   - PipelineID, ConversationID, Conversation, Provenance, and
     ResetConversation are already exposed.
   - Dispose removes only the pipeline mapping.

3. NlpPipeline operations are synchronous.
   - Analyze is stateless with respect to conversation state.
   - Ingest creates turns, provenance, mentions, and focus updates.
   - Ask creates turns and answer-side mentions but remains graph-read-only.

4. NlpResult and NlpAnswer expose enough data for the workbench:
   - NlpResult.Status, Diagnostics, Parsed, Frames, Chains, ReasoningResults,
     Question, Answer, and Provenance.
   - NlpAnswer.Status, Kind, Text, ShortAnswer, AnswerNodeID, Candidates,
     EvidencePaths, Question, Reasoning, UsesTemporaryEvidence, Confidence,
     Diagnostics, and UsesSessionProvenance.

5. ConversationContext exposes:
   - ConversationID, TurnIndex, Sequence.
   - FocusNodeID, LastSubjectNodeID, LastObjectNodeID, LastQualifierNodeID,
     LastAnswerNodeID, LastObjectOrQualifierNodeID.
   - Mentions and Provenance read-only lists.

6. The current Tools window is a placeholder and must remain one.
   - It contains only a TextBox listing planned Tools: Import, Export,
     Visualizer.
   - It has no core, pipeline, session, or input handling.
   - Phase 7 adds a separate NlpWorkbenchWindow and does not modify Tools.xaml
     or Tools.xaml.cs.

7. MainWindow currently:
   - Stores LRD_Core.Instance in a nullable field.
   - Initializes the core from Launch_Button_Click.
   - Opens a new Tools window on every Tools click.
   - Does not track or close an existing Tools window.
   - Has no NLP Workbench button or NlpWorkbenchWindow reference.

8. The WPF project targets net10.0-windows and uses standard WPF.
   - The smoke-test project targets net10.0.
   - The smoke-test project compiles OPEN-LRD/NLP/**/*.cs directly.
   - Therefore NlpWorkbench must live under OPEN-LRD/NLP to be headlessly
     testable.
   - XAML and code-behind can only be verified by build and manual UI checks.

9. Current test baseline:
   - 61 smoke tests pass.
   - Phase 6 added conversation, pronoun, focus, provenance, caveat, registry,
     read-only, and determinism groups.

10. No external UI framework, package, or service locator exists.
    The workbench must use the existing singleton explicitly and keep WPF
    event handling in the NLP Workbench window.

11. The WPF application has no existing session persistence.
    Closing the application loses graph and conversation state. The workbench
    must not imply otherwise.

12. WSL dotnet may be unavailable.
    Use the Windows SDK binary paths documented in Section 16.

Integration constraints:

- The NlpWorkbenchWindow must not construct NlpPipeline before the core is
  initialized.
- The existing Tools window must remain independent and must not require core
  initialization to open.
- Conversation IDs and pipeline IDs are GUIDs and must be displayed and copied
  verbatim.
- Attaching to an unknown conversation ID must not destroy the current session.
- Removing or clearing conversations must not delete graph nodes or links.
- Reset must clear only conversation memory, not the graph.
- Closing the NlpWorkbenchWindow must dispose its pipeline but must not remove
  the conversation.
- Core reinitialization invalidates the current workbench session.
  The workbench must detect stale mappings and transition to a no-session state.
- The workbench must never expose mutable conversation collections.

4. ARCHITECTURE AND FILE RESPONSIBILITIES
================================================================================

4.1 Separation of concerns

Use three layers:

1. Core and NLP layer
   - LRD_Core owns graph and conversation registries.
   - NlpPipeline owns one pipeline attachment.
   - ConversationContext owns session memory.

2. Workbench facade layer
   - NlpWorkbench owns one current pipeline.
   - It translates UI intentions into core and pipeline calls.
   - It returns NlpResult and NlpWorkbenchState snapshots.
   - It contains no WPF references and no MessageBox calls.

3. WPF presentation layer
   - NlpWorkbenchWindow.xaml defines controls and layout.
   - NlpWorkbenchWindow.xaml.cs handles user events, confirmations, and display formatting.
   - MainWindow owns application-level launch and NLP Workbench window lifetime.

4.2 NlpWorkbench responsibilities

NlpWorkbench must:

- Validate that the supplied core is not null.
- Tolerate an uninitialized core at construction, but refuse session operations
  until the core is initialized.
- Create a new conversation and pipeline when requested.
- Attach to an existing conversation by ID when requested.
- Reuse one NlpOptions instance for all pipelines it creates.
- Treat pipeline replacement transactionally.
- Dispose the old pipeline only after the new session is known to be valid.
- Provide ResetCurrentConversation, RemoveCurrentConversation, and
  ClearAllConversations.
- Expose Ingest and Ask that delegate directly to the current NlpPipeline.
- Expose RefreshState and State for display.
- Detect stale pipeline mappings after core reinitialization and clear the
  current pipeline reference.
- Dispose only its pipeline mapping on Dispose.

NlpWorkbench must not:

- Call LRD_Core.InitializeCore.
- Remove conversations implicitly when starting a new or attaching another
  conversation.
- Mutate graph nodes or links directly.
- Catch and swallow programming errors inside NlpPipeline.
- Reference WPF, System.Windows, or UI culture-specific formatting.
- Keep a second copy of mutable mentions or provenance data.

4.3 NLP Workbench window responsibilities

NlpWorkbenchWindow.xaml.cs must:

- Obtain LRD_Core.Instance.
- Create one NlpWorkbench for the window.
- Enable or disable controls based on workbench state.
- Show operation status without changing NlpResult semantics.
- Display raw diagnostics and evidence rather than hiding failures.
- Confirm reset, remove, and clear operations.
- Parse optional source and topic GUID fields.
- Handle empty input and unknown conversation IDs without crashing.
- Dispose the workbench when the window closes.

NlpWorkbenchWindow.xaml.cs must not:

- Instantiate NlpPipeline directly.
- Modify ConversationContext collections directly.
- Call LRD_Core.RemoveConversation without going through the workbench unless
  the workbench API explicitly requires it.
- Perform graph edits.
- Run NLP work on a background thread.

4.4 MainWindow responsibilities

MainWindow must:

- Keep the existing Launch Core workflow.
- Keep the existing Tools button and Tools window behavior unchanged.
- Add a separate NLP Workbench button.
- Disable the NLP Workbench button until Launch Core succeeds.
- Open one non-modal NlpWorkbenchWindow at a time.
- Activate and focus the existing NlpWorkbenchWindow if already open.
- Clear the stored NlpWorkbenchWindow reference on Closed.
- Avoid forcing the NlpWorkbenchWindow closed when the main window merely loses
  focus.

4.5 Proposed workbench API

The exact names may be adjusted during implementation, but the following shape is
the design baseline:

    internal sealed class NlpWorkbench : IDisposable
    {
        public NlpWorkbench(LRD_Core core, NlpOptions? options = null);

        public bool IsCoreInitialized { get; }
        public bool HasSession { get; }
        public Guid? PipelineID { get; }
        public Guid? ConversationID { get; }
        public NlpWorkbenchState? State { get; }

        public bool StartNewConversation();
        public bool TryAttachConversation(Guid conversationID, out string? error);
        public bool ResetCurrentConversation();
        public bool RemoveCurrentConversation();
        public void ClearAllConversations();
        public NlpResult Ingest(
            string? text,
            Guid? sourceNodeID = null,
            Guid? topicNodeID = null);
        public NlpResult Ask(string? text);
        public NlpWorkbenchState RefreshState();
        public void Dispose();
    }

Behavioral rules:

- StartNewConversation returns false when the core is uninitialized.
- StartNewConversation disposes the old pipeline after the new conversation is
  created successfully.
- TryAttachConversation first checks TryGetConversation. If the ID is unknown,
  it returns false and leaves the current session untouched.
- If the ID is valid, it disposes the old pipeline and creates a new pipeline
  attached to that ID.
- ResetCurrentConversation returns false when there is no current session.
- RemoveCurrentConversation removes the current conversation through the core
  and disposes the pipeline reference.
- ClearAllConversations calls core.ClearConversations and disposes the current
  pipeline reference.
- Ingest and Ask throw InvalidOperationException when there is no current
  session. The UI must prevent those calls while controls are disabled.
- Dispose does not remove the conversation.
- RefreshState never throws for a normal no-session state.

4.6 Proposed workbench state records

Add display-oriented immutable records, preferably in NlpTypes.cs:

    internal sealed record NlpWorkbenchState(
        bool CoreInitialized,
        bool HasSession,
        Guid? PipelineID,
        Guid? ConversationID,
        int TurnIndex,
        Guid? FocusNodeID,
        Guid? LastSubjectNodeID,
        Guid? LastObjectNodeID,
        Guid? LastQualifierNodeID,
        Guid? LastAnswerNodeID,
        int GraphNodeCount,
        int GraphLinkCount,
        int MentionCount,
        int ProvenanceCount,
        IReadOnlyList<ConversationMention> Mentions,
        IReadOnlyList<SessionProvenanceEntry> Provenance);

Optional presentation rows may live in NlpWorkbenchWindow.xaml.cs because they are WPF-only:

    internal sealed record MentionRow(...);
    internal sealed record ProvenanceRow(...);
    internal sealed record CandidateRow(...);
    internal sealed record DiagnosticRow(...);

Rules:

- The state snapshot is a copy of read-only views plus scalar counters.
- Do not expose the internal List<T> objects.
- Do not cache a stale state after a pipeline operation; refresh after every
  successful or failed Ingest/Ask.
- The workbench state reports node and link counts by reading the core
  dictionary. It must not call mutation APIs.
- Graph link count is the sum of each node's GetLinks count, matching the smoke
  test helper convention. If duplicate visual counting is undesirable in the
  UI, label the field "directed links" explicitly.

5. NLP WORKBENCH LIFECYCLE AND OPERATION SEMANTICS
================================================================================

5.1 Construction

- Constructor validates core is not null.
- Constructor stores the core and options.
- Constructor does not create a pipeline.
- If the core is initialized, the NLP Workbench window calls StartNewConversation after
  constructing the workbench.
- If the core is uninitialized, NlpWorkbenchWindow displays a disabled state.
  MainWindow should normally prevent this by enabling the NLP Workbench button
  only after launch.

5.2 Start new conversation

1. Verify core.initialized.
2. Create a new pipeline without an explicit conversation ID.
3. The core creates a fresh conversation and registers the pipeline mapping.
4. Dispose the old pipeline, if any.
5. Replace the current pipeline and conversation references.
6. Refresh state and return true.
7. The old conversation remains in the core registry and can be reattached by
   its conversation ID until explicitly removed or cleared.

5.3 Attach existing conversation

1. Verify core.initialized.
2. Reject Guid.Empty with a caller-visible error.
3. Call core.TryGetConversation.
4. If missing, return false with a message and keep the current pipeline.
5. If present, create a new pipeline using the requested conversation ID.
6. Dispose the old pipeline.
7. Replace references.
8. Refresh state and return true.
9. Sharing semantics are inherited: both old and new pipelines would share the
   same conversation if the old pipeline were still attached elsewhere.

5.4 Reset current conversation

1. Verify current pipeline exists and its conversation is still registered.
2. Call ResetConversation on the current pipeline.
3. Refresh state.
4. Do not dispose the pipeline.
5. Do not change graph counts.

5.5 Remove current conversation

1. Capture the current conversation ID.
2. Call core.RemoveConversation.
3. Dispose the current pipeline reference.
4. Set current pipeline and conversation to null.
5. Refresh state.
6. Graph counts must be unchanged.
7. If the removal returns false, still clear a stale local session reference and
   report that the session was no longer registered.

5.6 Clear all conversations

1. Confirm in the UI.
2. Call core.ClearConversations.
3. Dispose and clear the current pipeline reference.
4. Refresh state.
5. Graph counts must be unchanged.

5.7 Ingest

1. Require a current session.
2. Call pipeline.Ingest with the exact text and optional source/topic IDs.
3. Return the NlpResult unchanged.
4. The UI refreshes workbench state afterward so provenance, mentions, focus,
   and turn count are current.
5. Do not normalize, trim, or rewrite the user text in the workbench.
   Whitespace validation remains NlpPipeline behavior.

5.8 Ask

1. Require a current session.
2. Call pipeline.Ask with the exact question text.
3. Return the NlpResult unchanged.
4. The UI refreshes workbench state afterward.
5. Ask must remain graph-read-only. The workbench must not add graph inspection
   code that mutates graph state.

5.9 Refresh and stale-session detection

RefreshState must:

1. Determine CoreInitialized from core.initialized.
2. If a current pipeline exists, verify both:
   - core.TryGetPipelineConversation(pipelineID, out conversationID) succeeds.
   - core.TryGetConversation(conversationID, out _) succeeds.
3. If either check fails, the session is stale. Dispose the local pipeline
   reference, clear it, and return a no-session state.
4. Otherwise return a snapshot of the live context and graph counters.
5. If the core is uninitialized, return a no-session state without throwing.

The UI may display a specific message when it transitions from HasSession=true
to false because of core reinitialization.

5.10 Dispose

- Dispose the current pipeline only.
- Do not remove, reset, or clear the conversation.
- Do not call InitializeCore.
- Dispose must be idempotent.

6.4 UI state rules

- Disable destructive buttons during an operation.
- Use try/finally to re-enable controls after synchronous operations.
- Use confirmation MessageBoxes for Reset, Remove, and Clear All.
- Reset confirmation should mention that graph data is not deleted.
- Remove confirmation should mention that the conversation cannot be recovered.
- Clear confirmation should mention that all sessions are removed and the graph
  is unchanged.
- Copy Conversation displays a short success message or leaves a status-bar
  confirmation.
- Invalid GUID input must be shown inline or in the status area, not via a
  modal dialog unless the operation cannot continue.

6.5 Formatting rules

- Display GUIDs with the standard hyphenated format.
- Display null IDs as "(none)".
- Display counts using invariant integer formatting.
- Display confidence with a fixed number of decimal places, for example F2.
- Preserve diagnostic order from NlpResult.
- Preserve mention and provenance order from ConversationContext.
- Do not merge duplicate diagnostics in the UI; the pipeline already handles
  deduplication where appropriate.
- Do not hide Unsupported, NoMatch, Ambiguous, RejectedByTrust, or InvalidInput.
- Do not relabel No as failure; Yes and No are successful boolean answers.

6.6 Example end-to-end UI flow

1. Start the WPF application.
2. Click Launch Core.
3. Verify the NLP Workbench button becomes enabled.
4. Click NLP Workbench.
5. Verify a new conversation is created automatically and its ID is visible.
   Optionally click Tools and verify its placeholder text remains unchanged.
6. Ingest: "Alice works at Acme."
   - Status: Ingested.
   - Graph counts increase.
   - Provenance gains one or more entries.
   - Mentions include Alice and Acme.
7. Ask: "Where does she work?"
   - Status: Answered.
   - Short answer: Acme.
   - Answer text includes the session-provenance caveat.
   - The same graph counts remain; only conversation memory changes.
8. Click New Conversation.
   - Conversation ID changes.
   - Mentions and provenance are empty.
   - Ask "Where does she work?" returns Unsupported with a no-antecedent
     diagnostic.
9. Return to the first conversation by pasting its ID and clicking Attach.
   - The pronoun question works again.
10. Click Reset Conversation.
    - Mentions, focus, turn count, and provenance clear.
    - Ask "Where does she work?" is Unsupported again.
    - Graph counts are unchanged.
11. Click Remove Conversation.
    - The workbench returns to the no-session state.
12. Click New Conversation to continue.

7. SESSION AND CONVERSATION SEMANTICS IN THE UI
================================================================================

7.1 New versus attach

- New creates a brand-new conversation and does not delete prior sessions.
- Attach reuses an existing conversation ID and shares its mentions, focus,
  turn count, and provenance.
- This distinction must be visible in the UI text so the user does not assume
  that New clears old sessions.
- Clear All is the explicit bulk cleanup operation.

7.2 Reset

- Reset clears only the current conversation memory.
- TurnIndex and Sequence return to zero.
- Focus and last-role IDs become null.
- Mentions and provenance become empty.
- The ConversationID and pipeline mapping remain valid.
- The graph is untouched.
- The UI must refresh all session tabs immediately.

7.3 Remove

- Remove deletes the current conversation from the core registry.
- All pipeline mappings for that conversation are removed by the core.
- The workbench disposes its local pipeline reference.
- The graph is untouched.
- The UI must not silently create a replacement conversation.
- The user must click New Conversation or Attach.

7.4 Clear All

- Clear All removes every conversation and pipeline mapping from the core.
- The current workbench session becomes invalid.
- The graph is untouched.
- The UI enters the no-session state.

7.5 Closing the NLP Workbench window

- Closing the NLP Workbench window disposes only its workbench pipeline.
- The conversation remains in the core registry and may be reattached later in
  the same application run.
- Reopening the NLP Workbench window should create a new pipeline with a new
  conversation by default, unless the user attaches an existing ID.
- The Tools window is unrelated and keeps its existing placeholder behavior.
- Because the application has no persistence, all session state is lost when
  the application exits.

7.6 Single NLP Workbench window

- MainWindow stores a nullable NlpWorkbenchWindow reference.
- If the window is already open, clicking NLP Workbench activates it.
- If the user closes the NLP Workbench window, the reference is cleared.
- This prevents duplicate workbenches with competing input state.
- The conversation remains available for reattachment, so no work is lost.

7.7 Core reinitialization

- The NLP Workbench button should be enabled only after an explicit Launch Core.
- If code elsewhere calls InitializeCore again, the workbench must detect stale
  mappings on Refresh or before the next operation.
- The UI must show a clear "session no longer available" message and enter the
  no-session state.
- Do not attempt to reuse an old pipeline after core reinitialization.

================================================================================
9. ERROR HANDLING AND VALIDATION
================================================================================

9.1 Text input

- Empty or whitespace-only text is passed to the pipeline.
- The pipeline returns InvalidInput, and the UI displays its diagnostics.
- The UI must not show an unhandled exception for invalid text.
- Maximum length and token/sentence limits remain enforced by NlpPipeline.
- The UI should not duplicate pipeline limits in code; display pipeline
  diagnostics instead.

9.2 GUID inputs

- Blank source and topic fields mean null.
- A non-blank value must parse as a Guid.
- Invalid GUID text produces an inline or status-area validation message.
- The workbench must not call Ingest when GUID validation fails.
- If a supplied source or topic node ID does not exist, show a status-area error
  and do not call Ingest.
- Validate source and topic only when provided.
- Optional stricter validation: source node type should be NodeTypes.Sources.
  If enforced, state the requirement in the UI label and tests.

9.3 Unknown conversation ID

- Attach must catch the core's missing-conversation condition or use
  TryGetConversation first.
- The current session must remain intact.
- The UI must show a message such as:
  "Conversation '<id>' was not found. The current session was not changed."

9.4 No session

- Ingest, Ask, Reset, Remove, and Copy are disabled.
- If a stale event fires, the workbench throws InvalidOperationException and
  the UI shows a status message rather than crashing.
- New and Attach remain available.

9.5 Unexpected exceptions

- Wrap event-handler bodies in try/catch at the UI boundary.
- Show a MessageBox with the operation name and exception message.
- Do not include stack traces in normal user-facing text.
- Keep the existing workbench and display state where possible.
- Refresh state after the catch.
- Do not hide exceptions from the smoke tests.

9.6 Destructive confirmations

- Reset: confirmation required.
- Remove: confirmation required.
- Clear All: confirmation required.
- New and Attach: no confirmation required.
- Closing the NLP Workbench window: no confirmation required because it does
  not remove sessions.
- Do not prompt twice for the same click.

9.7 Reentrancy

- Synchronous operations run on the UI thread.
- Disable operation buttons before calling the workbench.
- Use try/finally to restore button state.
- Do not support concurrent Ingest or Ask calls.
- Do not add Task.Run, timers, or async/await in Phase 7 unless a later review
  explicitly requests it.

   - ClearAllConversations.

   - Dispose the workbench.

   - The conversation still exists in the core.

================================================================================
14. RISKS, DECISIONS, AND DEFERRED WORK
================================================================================

Resolved design decisions for Phase 7:

- Use a UI-independent NlpWorkbench under OPEN-LRD/NLP so lifecycle and state
  are testable in the net10.0 smoke project.
- Keep NlpWorkbenchWindow.xaml.cs as the WPF boundary; do not introduce an MVVM framework.
- Keep the existing Tools window and Tools button unchanged as placeholders.
- Allow only one NLP Workbench window per MainWindow instance.
- Enable the NLP Workbench button only after Launch Core succeeds.
- Start a fresh conversation automatically when the NLP Workbench window opens
  with an initialized core.
- New Conversation does not delete prior sessions.
- Attach is explicit by conversation ID.
- Remove and Clear All are the only destructive registry operations.
- Closing or disposing a workbench does not remove the conversation.
- Reset clears conversation memory only.
- Workbench operations are synchronous on the UI thread.
- No background threads, cancellation, or async pipeline work in Phase 7.
- Optional source and topic inputs are GUID text boxes, not graph pickers.
- Validate optional source/topic IDs for parseability and existence before
  ingestion.
- Preserve raw NlpResult semantics in the UI; do not reinterpret statuses.
- Keep Import, Export, and Visualizer visibly deferred.
- Do not add persistence or graph serialization.
- Do not change Module 1 or Module 2 models.

Known Phase 7 limitations after implementation:

- WPF UI automation is not part of the smoke suite.
- The UI is English-only and desktop-only.
- No durable session or graph persistence.
- No session expiry.
- No source/topic picker; IDs are entered as text.
- No graph visualization or editing.
- No async progress or cancellation for large inputs.
- Large graph counts and session lists are displayed without virtualization
  tuning beyond standard WPF DataGrid behavior.
- Session IDs must be copied and stored manually to reattach later.
- Core reinitialization invalidates existing sessions by design.

Deferred beyond Module 3:

- Import, Export, and Visualizer tools.
- Durable provenance and persistence.
- Graph editing and visualization.
- Async pipeline execution and progress reporting.
- Rich answer rendering and source citation UI.
- Multi-user sessions and remote services.
- Additional NLP algorithms or statistical models.
